# Supply Chain Security

Goal: Neither a compromised dependency, a tampered build tool or CI action, nor a subverted release artifact should bring code onto users' machines unnoticed. The client handles a UEX secret key and runs alongside the game – a compromised build would be a direct attack on the users.

**Honest limit:** Supply chain security is risk reduction, not a guarantee. The following measures primarily prevent *unnoticed* changes (tampered artifacts, re-pointed tags, silently bumped versions). Against a maintainer who publishes a malicious, correctly signed version, only a cooldown period, review and a small number of dependencies help.

## 1. Threat model

| # | Attack vector | Example |
|---|---|---|
| T1 | Tampered or replaced artifact in the repository or in transit | Artifact is replaced after publication; a mirror delivers different bytes |
| T2 | Malicious **new version** of a genuine dependency (maintainer account takeover) | Patch release with malicious code is adopted automatically |
| T3 | Typosquatting or dependency confusion via additional repositories | Package with the same name in JitPack or `mavenLocal` |
| T4 | Tampered **Gradle wrapper** (`gradle-wrapper.jar`) or tampered Gradle distribution | Modified JAR in a PR |
| T5 | Compromised **GitHub Action** (tag is re-pointed to a malicious commit) | Incident involving `tj-actions/changed-files` (March 2025) |
| T6 | Tampered **binary assets and build tools**: ONNX models, native libraries, the build's JDK, installer tooling (WiX, `dpkg-deb`/`fakeroot`) | Replaced model from Hugging Face; JDK download; modified WiX on the build machine |
| T7 | Tampering **after** the build (release files replaced) | Installer in the release is swapped |
| T8 | Native libraries that are extracted at runtime into a **shared temp directory** (DLL/SO planting) | sqlite-jdbc and ONNX Runtime extract natives to `java.io.tmpdir` by default |
| T9 | Runtime loading of code or models from unversioned sources | Model download "latest"; auto-update without signature verification |
| T10 | Optional AI models via Ollama (downloaded by the user) | Tampered model in a third-party registry |

## 2. Measures

### 2.1 Resolving dependencies (T1–T3)

| ID | Measure | Implementation |
|---|---|---|
| S-1 | **Only two repositories:** Maven Central for libraries, Gradle Plugin Portal only for plugins. No `mavenLocal()`, no JitPack, no snapshot repos. | `settings.gradle.kts`: `dependencyResolutionManagement { repositoriesMode = RepositoriesMode.FAIL_ON_PROJECT_REPOS }`; repository content filter (`exclusiveContent`/`content { includeGroup… }`) for the Plugin Portal |
| S-2 | **Only fixed versions** from the version catalog; no dynamic versions (`+`, `latest.release`, ranges), no `SNAPSHOT`s | `resolutionStrategy { failOnDynamicVersions(); failOnChangingVersions() }` in `build-logic` for all project configurations; plugin versions are fixed in the catalog / `pluginManagement` (the convention plugin does not reach plugin and buildscript resolution, so those are covered by S-3 locking and S-4 verification) |
| S-3 | **Dependency locking** in all four places: project configurations, buildscript classpath, settings classpath (Foojay plugin) and the `build-logic` included build; transitive versions are frozen (one exception, see the next column) | `dependencyLocking { lockAllConfigurations() }` per project (one `gradle.lockfile` per project – it does **not** cover the buildscript), plus `buildscript { configurations.classpath { resolutionStrategy.activateDependencyLocking() } }` (`buildscript-gradle.lockfile`), settings and `build-logic` locking; all lockfiles checked in; changes only via `--write-locks` in a separate commit. **Exception:** tools that plugins resolve in detached configurations at task execution time (currently google-java-format via Spotless) are not covered by `lockAllConfigurations()`. Their direct version is fixed in the catalog and their artifacts are pinned by S-4 verification. They do not appear in the lockfiles, so the blocking S-19 run does not cover them; only its report-only run sees them through `verification-metadata.xml` (acceptable: S-19 blocks runtime dependencies only). |
| S-4 | **Dependency verification:** a SHA-256 checksum for **every** artifact plus a PGP signature check **wherever the artifact is signed** (Gradle: use both for integrity and authenticity). Maven Central artifacts are signed; many Gradle Plugin Portal artifacts are **not** (checked: no `.asc` for the jlink and errorprone plugins), so plugins will mostly be checksum-only, with a justification (S-6). | `gradle/verification-metadata.xml` with `verify-metadata` and `verify-signatures` = `true`, `<key-servers enabled="false"/>` and `<keyring-format>armored</keyring-format>`. Keys come only from the committed `gradle/verification-keyring.keys` and are never fetched at build time. `gradle/verification-keyring.gpg` is in `.gitignore`, because Gradle prefers the binary keyring when both exist. A build with an unknown artifact or key **fails**.<br/>• **CI guard** (runs before the first Gradle call, like S-12): every CI Gradle invocation passes `--dependency-verification strict`, because command-line options override `gradle.properties`. The job fails if any of the following holds:<br/>• `org.gradle.dependency.verification` appears in `**/gradle.properties`, `**/*.gradle.kts`, `gradlew*` or `.github/**`, or `--dependency-verification` appears there with any value other than `strict`;<br/>• `verification-metadata.xml` lacks one of the settings above;<br/>• `gradle/verification-keyring.gpg` exists;<br/>• an artifact entry has no `sha256`.<br/>The tagged R-SEC-2 test (M0) checks the same rules. |
| S-5 | **New keys or checksums only with review:** `verification-metadata.xml` is updated in the **same PR as the dependency change, as a separate commit**, in two runs, so that signed artifacts keep a checksum too: `./gradlew --write-verification-metadata sha256 help check`, then `./gradlew --write-verification-metadata pgp,sha256 --export-keys help check`. Why two runs and these tasks:<br/>• a single `pgp,sha256` run writes checksums only for unsigned artifacts and ignored keys;<br/>• `help` alone misses tools that plugins resolve in detached configurations only when their task runs (e.g. Spotless → google-java-format, S-3);<br/>• a change that affects release tasks also runs `cyclonedxBom` and the jlink/jpackage tasks.<br/>The diff shows every new key or hash. New key fingerprints are checked against the publisher's project page or release announcement and documented in the PR. Every new `<ignored-key>` and every entry with `origin="Generated by Gradle"` is justified in the PR (S-6). | `.github/CODEOWNERS`: `gradle/**` (verification metadata, keyring, version catalog, wrapper), `gradlew`, `gradlew.bat`, `**/gradle.properties`, `**/*.gradle.kts` (incl. `settings.gradle.kts`), `build-logic/**`, `**/*.lockfile`, `.github/**` (workflows, `dependabot.yml`, scripts, `CODEOWNERS` itself), `osv-scanner.toml`, the JDK pin file (S-11), `NOTICE`, the OCR asset directory with its checksum file (S-22) and `shared-kernel/**` (09 §2) → review by the maintainer mandatory |
| S-6 | Artifacts without a signature (if unavoidable) only with a checksum and an **explicit justification** in `verification-metadata.xml` (comment "why no PGP") | Review |

### 2.2 Updates (T2)

| ID | Measure | Implementation |
|---|---|---|
| S-7 | **Cooldown period for new versions:** Dependabot proposes version updates no earlier than **7 days** after publication. Experience shows that compromised releases are often discovered within days. **Security updates** are exempt from this. | `.github/dependabot.yml`: `cooldown: default-days: 7` (if not specified, the GitHub docs state a default of 3 days); ecosystems `gradle` and `github-actions` |
| S-8 | Updates individually or in small groups, never auto-merged; every update updates the lockfile **and** the verification metadata in the same PR (Dependabot cannot do this itself → manual follow-up commit) | Review checklist in 09 §11 extended |
| S-9 | For every update, briefly check: changelog, new transitive dependencies (diff in the lockfile), new signing key? | PR template |

### 2.3 Build tools (T4, T6)

| ID | Measure | Implementation |
|---|---|---|
| S-10 | **Secure the Gradle wrapper:** `distributionSha256Sum` in `gradle/wrapper/gradle-wrapper.properties`. CI checks `gradle-wrapper.jar` against the official checksums **and** parses `gradle-wrapper.properties` as Java properties (the generated file escapes `:` as `\:`, so a literal grep is not enough): `distributionUrl` must start with `https://services.gradle.org/distributions/` and `distributionSha256Sum` must be present. Pinning the host forces the checksum to match a genuine distribution; a version change is visible in review (S-5). | `gradle/actions/wrapper-validation` (gradle/actions v6.4.0, pinned by commit SHA) plus the properties check, in every workflow before the first Gradle invocation |
| S-11 | **Build JDK and installer tools pinned and verified:** the JDK of the release build becomes the runtime in every installer. It is obtained explicitly via `actions/setup-java`, not via the toolchain auto-download. Installer tools come from the runner image or are pinned. | • `actions/setup-java` (SHA-pinned) with `distribution: temurin` and the exact release including the build number (never `27` or `latest`), from one versioned file read via `java-version-file` (M0 checks that the exact build resolves). `verify-signature: true` makes failures fatal. `force-download: true` and `cache-jdk: false` are set, because otherwise a JDK from the tool cache or the Actions cache is used without being verified again.<br/>• If Adoptium rotates its signing key, the build fails. The new key goes into `verify-signature-public-key` only after its fingerprint is checked against adoptium.net and documented in the PR (as in S-5); `verify-signature: false` is never the fix.<br/>• Dependabot does not update the JDK pin. A scheduled CI job compares it with the latest Temurin release of the same line and fails when it is behind (security release, [release-process.md](../release-process.md)).<br/>• Installer tools: jpackage uses the WiX Toolset 3.14.1 preinstalled on `windows-latest` and `dpkg-deb`/`fakeroot` on `ubuntu-latest`. The GitHub-hosted runner image is an accepted trust anchor, like the runner itself. The release build jobs (S-14) log `ImageOS`/`ImageVersion` and the tool versions and fail if WiX is not the expected version; the release notes record the JDK build and the tool versions. A build or CI tool that is not on the image is installed only at a fixed version with a verified checksum, as a documented S-1 exception for build tools (owner decision); the OSV-Scanner binary (S-19) is the one such exception so far.<br/>• `org.gradle.java.installations.auto-download=false` in CI; locally Foojay may be used, releases are built **only** in CI. |
| S-12 | No build scripts from the network (`apply(from = "https://…")`), no plugins outside the catalog | ArchUnit cannot check this → review plus CI grep for `apply(from` with a URL |

**Downloads outside the build** (e.g. a JDK or JavaFX JARs fetched in a working session for a spike) are never committed and are verified like build inputs before anything from them runs: a PGP signature checked against a key whose fingerprint is confirmed from a second, independent source, or a SHA-256 from a source other than the download host. A `.sha1`/`.md5` next to the artifact only detects transport errors. JavaFX comes only from the Maven Central platform JARs, never from an SDK download (S-24).

### 2.4 CI/CD (T5, T7)

| ID | Measure | Implementation |
|---|---|---|
| S-13 | **Pin actions by full commit SHA** (version as a comment), never by tag or branch. An action counts as pinned only when the code it runs is pinned. Actions that run a container image by tag (`runs.using: docker` with `docker://…:<tag>`, e.g. `google/osv-scanner-action`) are not used, and tool binaries that a workflow downloads are pinned by SHA-256 (S-19). | `uses: actions/checkout@<40-hex-sha> # v7.0.1`; Dependabot (`github-actions`) updates SHA and comment |
| S-14 | **Minimal permissions, separated duties:** `permissions: contents: read` as the workflow default. Write permissions and secrets only in jobs that do not run the build:<br/>• **Release:** a build matrix (`windows-latest`, `ubuntu-latest`) with `contents: read`, `actions/checkout` with `persist-credentials: false` and no secrets runs Gradle (jpackage, archives, `cyclonedxBom`, packaged-app smoke test) and uploads the outputs with `actions/upload-artifact`. A separate `publish` job (`needs` the build; environment "release", S-15) never checks out or runs Gradle. It downloads the outputs (`actions/download-artifact`), computes `SHA256SUMS`, attests them (S-16) and creates the GitHub release. Only this job gets `contents: write`, `id-token: write`, `attestations: write` and `artifact-metadata: write`; a future signing certificate (S-21) is a secret of this environment only.<br/>• **Dependency submission:** a separate job (`contents: write`, triggered only on push to `main`, because forked PRs never get write tokens).<br/>• **OSV scan** (S-19): `contents: read`, no SARIF upload.<br/>• **Live API drift job** (04 M1): `contents: read`, triggered only by `schedule`/`workflow_dispatch` on `main`, never on pull requests. The key of a dedicated UEX test account comes from a protected environment restricted to `main` and is exposed only to the step that runs the prebuilt API-spike CLI.<br/>Honest limit: the split keeps build code away from the release and attestation tokens; it does not detect malicious output of the build itself (T2, S-7 to S-9). | Workflow review; no `pull_request_target` with checkout of PR code |
| S-15 | Release builds only from **protected tags** on protected `main`; the publish job (S-14) runs in a GitHub environment with approval | Branch/tag protection, environment "release" |
| S-16 | **Build provenance (SLSA):** every release artifact gets a signed attestation | `actions/attest` v4.2.2 (SHA-pinned; provenance mode; the `attest-build-provenance` wrapper, which only calls `actions/attest`, is not used). It runs in the publish job on the downloaded artifacts (S-14), so attestation is separated from the build steps. Users can verify with `gh attestation verify`. **Precondition:** the repository is public – on GitHub Free/Pro/Team, artifact attestations exist for public repositories only. If its visibility ever changes, R-SEC-6 cannot be met, and releases are blocked until the project owner decides on a replacement (S-21 is optional and covers Windows only). |
| S-17 | **Checksums** (`SHA256SUMS`) for all artifacts; verification instructions in the README | Publish job (S-14), computed over the downloaded artifacts |
| S-18 | **SBOM** (CycloneDX) for every release, as a release asset. It also lists the bundled runtime (vendor and exact version) and the OCR assets with SHA-256 (once bundled). Whether the CycloneDX plugin can add these or a merge step is needed is checked in M1. | Gradle plugin `org.cyclonedx.bom` 3.5.0, run in the release build jobs (S-14) |
| S-19 | **Vulnerability scan** in every PR, daily on `main` and daily on the latest release tag: known vulnerabilities with CVSS ≥ 7.0 (or without a score, until triaged) in runtime dependencies **block** the merge; on the latest release tag they start a security release ([release-process.md](../release-process.md)). | OSV-Scanner CLI v2.6.0 (`google/osv-scanner`), release binary `osv-scanner_linux_amd64`, checked against a SHA-256 committed in the repository. The hash is taken from the release's `osv-scanner_SHA256SUMS` when the version changes; Dependabot does not update it, so a version bump is a manual PR reviewed per S-8/S-9. No GitHub Action, no container image (S-13), no SARIF upload, `contents: read` (S-14).<br/>• **Blocking run:** `osv-scanner scan source --format json` over every project `gradle.lockfile` outside `build-logic`. OSV-Scanner has no severity or configuration filter, so a checked-in gate script (`.github/scripts/`, CODEOWNERS) keeps only packages whose `group:artifact:version` is on a lockfile line whose configuration list contains `runtimeClasspath`. It fails if a remaining vulnerability group has `max_severity` ≥ 7.0 or no severity at all (fail closed until triaged). The job first runs the script against recorded JSON fixtures.<br/>• **Report-only run:** `verification-metadata.xml` and the buildscript, settings and `build-logic` lockfiles (build and test tooling) are reported but do not block.<br/>• **Exceptions** only in `osv-scanner.toml` as `[[IgnoredVulns]]` with `id`, `reason` and a mandatory `ignoreUntil` (CODEOWNERS). |
| S-20 | Report the dependency graph to GitHub so that Dependabot alerts also see transitive Gradle dependencies | `gradle/actions/dependency-submission` |
| S-21 | Optional: code signing of the Windows installers (Authenticode) against SmartScreen warnings and tampering | Costs a certificate → decision of the project owner; until then attestation plus checksums |

### 2.5 Binary assets and runtime (T6, T8, T9, T10)

| ID | Measure | Implementation |
|---|---|---|
| S-22 | **OCR assets** – the det model, the rec model and the file that carries the character dictionary (a `.txt` or an inference config such as `inference.yml`; which one is checked at integration) – are obtained once at a fixed Hugging Face revision (commit hash, not `main`) and committed (each well below the 50 MB limit); the build never fetches them. Every asset is listed with path, Hugging Face repo, revision and SHA-256 in one checksum file (e.g. `models/SHA256SUMS`) and in `NOTICE`. A Gradle verify task runs before `processResources`/`test`, so also in `./gradlew check` and for `tools/ocr-eval`; the app verifies every asset when loading. Mismatch = abort with a clear message. A model update is a reviewed PR that changes the assets and the checksum file together. | `adapter-ocr` (loading), `build-logic` (build check) |
| S-23 | **No runtime downloads of code or OCR models.** Optionally downloadable models (e.g. additional writing systems, R-L10N-3) only from fixed, configured URLs with a fixed, stored SHA-256 | Review; `adapter-ocr` |
| S-24 | **Do not extract natives into the shared temp:** sqlite-jdbc and ONNX Runtime load their natives from an app-specific directory (shipped in the jlink image or extracted into a user-owned, non-world-writable directory) | Verified property names: ONNX Runtime `onnxruntime.native.path` (ORT still creates an owner-only random temp dir, low risk); sqlite-jdbc `org.sqlite.lib.path` + `org.sqlite.lib.name` (avoids extraction; `org.sqlite.tmpdir` only moves it, and the extracted file is world-readable); JavaFX: natives are copied at build time from the verified Maven Central platform JARs into the runtime image (`bin/javafx/` on Windows, `lib/` on Linux). `NativeLibLoader` checks that directory first for jlinked modules (checked in the OpenJFX 27 source), so nothing is extracted. Defence in depth: the `app` bootstrap sets `javafx.cachedir` to an owner-only directory in the app's cache directory (02 §8; portable marker honoured); otherwise JavaFX would use `~/.openjfx/cache`, falling back to `${java.io.tmpdir}/.openjfx_<user>`. JavaFX jmods are a download outside S-1. They are used only if M0 shows that jlink with the modular JARs fails, and then only as a documented S-1 exception: pinned URL and SHA-256 checked in `build-logic` before jlink (as in S-22), entries in T6 and in the SBOM, and an update to the CLAUDE.md supply-chain rules. Plus `--enable-native-access` for the modules that load natives (JEP 472; for ORT in the jlink image this is the merged module, 02 §8). The packaged-app smoke test (04 M1) fails if a `.openjfx` or `.openjfx_<user>` directory is created or a native-access grant is missing. |
| S-25 | **Update notice without auto-update:** the app only shows "new version available" with a link to the GitHub release page; it downloads and launches nothing by itself | `adapter-platform` |
| S-26 | **TLS everywhere, with one exception for Ollama:** UEX, the update check and any `https://` Ollama host use TLS. Plain HTTP is allowed only to a loopback Ollama host (R-VLM-6), or to a non-loopback `http://` Ollama host that the user confirmed after the notice that panel crops travel unencrypted. Certificate verification is never disabled (not even "for debugging"), and no dialog offers to skip it. | One reviewed composite `X509ExtendedTrustManager` (Windows-ROOT/Linux system bundle + JDK store) that forwards the `SSLEngine`/`Socket` overloads, so hostname verification stays on; ArchUnit: no other `TrustManager` implementations; CI check forbids the property `jdk.internal.httpclient.disableHostnameVerification`; test against a wrong-host certificate. (`HostnameVerifier` is not used by `java.net.http` and is banned.) UEX hosts: `https` only, from the R-API-3 list or the confirmed expert host, no redirects. WireMock test in `adapter-uex`: an `http` host, or a host that is neither on the list nor the confirmed expert host, never receives the secret-key header (`secret_key`, spelling unverified, [06](06-uex-api.md)) or the `Authorization` header, and a 3xx response to another host is not followed. |
| S-27 | **Ollama models (optional):** the app downloads no model itself; it asks the local Ollama to pull the recommended model on request (R-VLM-7). After every pull and every `/api/tags` check, it compares the active model's name and digest with the evaluated-model list shipped with the release (R-VLM-11). A model that matches no entry counts as **not evaluated**: a re-pushed tag (the digest also changes when only the template or parameters change), or any other model. The UI says so, and its readings stay below the send threshold (07 §2.7); only a later release that adds the digest after a bake-off lifts this. The comparison relies on assumption A20. Remote (cloud) models need consent (R-VLM-6). Recommend models only from the official Ollama registry. The integrity of the download itself is Ollama's responsibility, not ours. | `adapter-vlm`, R-VLM-7, R-VLM-11 |

### 2.6 Repository and process

| ID | Measure |
|---|---|
| S-28 | Branch protection for `main`: PR required, green CI, review by CODEOWNERS, no force push; 2FA for all maintainers |
| S-29 | **Few dependencies** (09 §9): every new dependency needs a justification, a license check and a look at its maintenance status. Is there a PGP key on Central? How many maintainers? |
| S-30 | **Reproducibility:** Gradle 9 archive tasks are reproducible by default (deterministic order, fixed timestamps, directories 0755, files 0644). This is not overridden globally, with one exception: the Linux app-image `tar.gz` task calls `useFileSystemPermissions()`, so that the launcher and the runtime binaries keep the modes jpackage gave them. The packaged-app smoke test (04 M1) asserts that `<App>/bin/<App>` and `lib/runtime/lib/jspawnhelper` are executable. Honestly: jpackage installers (MSI/deb) are not bit-for-bit reproducible; the attestation (S-16) partially compensates for this. |
| S-31 | Security reports: `SECURITY.md` with a reporting channel (privately via GitHub Security Advisories); a confirmed report starts a security release ([release-process.md](../release-process.md)) |

## 3. What this achieves in practice

| Threat | Covered by | Residual risk |
|---|---|---|
| T1 tampered artifact | S-3, S-4 (hash for every artifact, signature where signed) | low |
| T2 malicious new version | S-7 cooldown period, S-8/S-9 review, S-19 scan | **medium** – a correctly signed malicious version from a genuine maintainer is only detected through time and review |
| T3 typosquatting/confusion | S-1, S-2, S-5 | low |
| T4 wrapper/Gradle | S-5, S-10, S-4 (CI guard) | low |
| T5 actions | S-13, S-14 | low |
| T6 models/natives/JDK/installer tools | S-4, S-11, S-19 (OSV binary), S-22 | low; tools preinstalled on the GitHub runner image (WiX 3, `dpkg-deb`, `fakeroot`) are trusted like the runner itself |
| T7 tampering after build | S-16, S-17 | low, provided users verify; without code signing (S-21) very few do |
| T8 native planting | S-24 | low after implementation |
| T9 runtime loading | S-23, S-25 | low |
| T10 Ollama models | S-27 | **medium** – outside our control; the feature is optional and local |
