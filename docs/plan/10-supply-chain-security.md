# Supply Chain Security

> **Doc type:** Living spec — binding. Last reviewed: 2026-10-13.

Goal: Neither a compromised dependency, a tampered build tool or CI action, nor a subverted release artifact should bring code onto users' machines unnoticed. The client handles a UEX secret key and runs alongside the game – a compromised build would be a direct attack on the users.

**Honest limit:** Supply chain security is risk reduction, not a guarantee. The following measures primarily prevent *unnoticed* changes (tampered artifacts, re-pointed tags, silently bumped versions). Against a maintainer who publishes a malicious version, only a cooldown period, review, audits and a small number of dependencies help. crates.io publishes no signatures, so authenticity of a crate rests on its checksum in `Cargo.lock`, the audits of S-4 and the review of S-5, not on a signing key.

Amended 2026-10-12: the measures were re-expressed for Cargo after the move from Java 27, JavaFX and Gradle to Rust and egui ([ADR-0005](../adr/0005-rust-and-egui.md), D8). Measure IDs are unchanged; a Gradle-specific measure without a Rust counterpart is marked `Withdrawn (2026-10-12)` and keeps its row. Tools and crates that this document names without a version are chosen and verified at source in M0.

## 1. Threat model

| # | Attack vector | Example |
|---|---|---|
| T1 | Tampered or replaced artifact in the registry or in transit | A crate archive is replaced after publication; a mirror delivers different bytes |
| T2 | Malicious **new version** of a genuine dependency (maintainer account takeover) | Patch release with malicious code is adopted automatically |
| T3 | Typosquatting or dependency confusion via additional sources | A crate with the same name pulled from a git URL, an alternative registry or a `[patch]` entry |
| T4 | Tampered **Rust toolchain** or Cargo configuration | Modified `rust-toolchain.toml`, a `.cargo/config.toml` that redirects the registry or sets `RUSTC_WRAPPER`, a toolchain from an unofficial channel |
| T5 | Compromised **GitHub Action** (tag is re-pointed to a malicious commit) | Incident involving `tj-actions/changed-files` (March 2025) |
| T6 | Tampered **binary assets and build tools**: ONNX models, the ONNX Runtime library, the build's Rust toolchain, installer tooling (`cargo-packager`, WiX, `dpkg-deb`/`fakeroot`), CI tools (OSV-Scanner, gitleaks, actionlint, zizmor, `reuse`, `cargo-deny`, `cargo-vet`) | Replaced model from Hugging Face; ONNX Runtime fetched from an unpinned host; modified WiX on the build machine |
| T7 | Tampering **after** the build (release files replaced) | Installer in the release is swapped |
| T8 | Native libraries that are loaded from a **writable or shared location** (DLL/SO planting) | The ONNX Runtime library found through the current directory or a shared temp directory instead of the installation directory |
| T9 | Runtime loading of code or models from unversioned sources | Model download "latest"; auto-update without signature verification |
| T10 | Optional AI models via Ollama (downloaded by the user) | Tampered model in a third-party registry |
| T11 | Secret committed to the repository or exposed in CI | UEX key in a test fixture, a recorded response or a log |
| T12 | Unsafe workflow | Template injection through a pull-request title; excessive token permissions; an unpinned tool download |
| T13 | Licence contamination or missing notices | A GPL-incompatible shipped dependency; a release without the ONNX Runtime notices or the source archives |
| T14 | Code that runs **at build time** from a dependency: `build.rs` scripts and procedural macros | A build script that downloads and executes a binary, reads secrets from the environment or patches other crates |

## 2. Measures

### 2.1 Resolving dependencies (T1–T3)

| ID | Measure | Implementation |
|---|---|---|
| S-1 | **Only one registry:** crates.io for libraries and build tools that are crates. No git dependencies, no path dependencies outside the workspace, no alternative registries, no `[patch]` or `[replace]` sections, no `mavenLocal`-style local overrides. **Recorded exceptions:** (1) CI tools outside Cargo (S-36: GitHub releases, PyPI); (2) the ONNX Runtime library and, if the crate fetches it from a host of its own, that host: how the library reaches the build is decided in M0 (O-108) so that it is pinned by SHA-256 (S-22); a fetch that is not checksum-pinned is not allowed; (3) the installer tooling of S-11 (WiX release asset). | `deny.toml`: `[sources]` with `unknown-registry = "deny"`, `unknown-git = "deny"`, an empty allow-list except crates.io; `[bans] wildcards = "deny"`. The CI guard of S-4 rejects `[patch]`, `[replace]`, `[source]` or `[registries]` entries and `registry`/`git`/`path`-outside-workspace dependency keys in any `Cargo.toml` or `.cargo/config.toml` |
| S-2 | **Only fixed versions:** every dependency is declared once in `[workspace.dependencies]` of the root `Cargo.toml`; no wildcard (`*`) requirements, no git branches or revisions, no pre-release versions. **Recorded exception:** `ort` as a release candidate, pinned exactly (`=2.0.0-rc.13`; ADR-0005 D2, 09 §3b). The Rust toolchain is pinned to an exact version in `rust-toolchain.toml` (never `stable`). Whether further requirements use the exact `=` form or the default caret form is decided in M0; the lockfile (S-3) is what freezes the resolved versions either way. | `cargo-deny` `wildcards = "deny"` and a check in the `xtask` that every member crate inherits its dependencies from `[workspace.dependencies]`; the CI guard of S-4 rejects a pre-release version outside the recorded exception |
| S-3 | **Dependency locking:** the root `Cargo.lock` is committed and covers libraries, build scripts, procedural macros, dev-dependencies and the `xtask` and tool crates of the one workspace, so there is no separate "buildscript" or "settings" classpath. Every CI invocation of cargo passes `--locked` (and `--frozen` where nothing may be fetched); a build whose lockfile would change fails. Transitive versions are frozen. Changes only via `cargo update -p` or `cargo add` in a separate commit. A separate workspace (for example a fuzzing crate) has its own committed lockfile under the same rules. | `.github/workflows/`, the CI guard of S-4; Dependabot's lockfile changes are reviewed per S-8 |
| S-4 | **Checksum verification and audits:** Cargo records a SHA-256 `checksum` in `Cargo.lock` for every registry package and verifies every download against it; `cargo vendor` output is verified against the same checksums and a committed per-package hash list (decided 2026-10-13, O-120: the vendored tree is regenerated in CI and compared with the committed hash list, not committed; measured 2026-10-13, the planned dependency set vendors to 555 to 572 crates, about 608 to 719 MiB on disk and 91 to 99 MiB compressed, against about 3 MB of checksum data). **Authenticity** cannot come from signatures, because crates.io has none: it comes from `cargo-vet` audits (the `supply-chain/` files are committed; imports only from audit sources named in the pull request, exemptions only with a `notes` entry that justifies them, S-6) and from the review of S-5. **PGP verification of artifacts is withdrawn** (no Rust counterpart); the CI guard and audits replace it. | `cargo vet` in CI, blocking; `cargo deny check sources` and `cargo deny check bans`.<br/>• **CI guard** (runs before the first cargo call, like S-12): every CI cargo invocation passes `--locked`. The job fails if any of the following holds:<br/>• `Cargo.lock` has a `[[package]]` with a `source` but no `checksum`, or a `source` other than the crates.io registry;<br/>• a `Cargo.toml`, a `.cargo/config.toml`, `rust-toolchain.toml` or any file under `.github/**` contains `[patch]`, `[replace]`, `[source]`, `[registries]`, a `registry`/`git` dependency key, a `RUSTC_WRAPPER`, `CARGO_REGISTRIES_*`, `CARGO_SOURCE_*` or `CARGO_NET_GIT_FETCH_WITH_CLI` override, or `--locked` is dropped from a cargo call;<br/>• `rust-toolchain.toml` does not name an exact version;<br/>• a vendored package differs from its recorded hash.<br/>The tagged R-SEC-2 test (M0) checks the same rules. |
| S-5 | **New crates or checksums only with review:** `Cargo.lock` and the `supply-chain/` files are updated in the **same PR as the dependency change, as a separate commit**. The diff shows every new crate, version and checksum. For each new crate the PR documents: purpose, SPDX licence, crates.io owners and last release, the repository it links to (and that it matches), whether it has a build script, procedural macro or native code (S-12, 09 §3b), and its `cargo-vet` status (audit, import or justified exemption, S-6). A crate that changes owners or whose source repository moves is treated as new. | `.github/CODEOWNERS`: `Cargo.toml` and `**/Cargo.toml`, `Cargo.lock`, `.cargo/**`, `rust-toolchain.toml`, `deny.toml`, `clippy.toml`, `supply-chain/**` (audits, config, imports), the vendor hash list (S-4), the build-script review list (S-12), `xtask/**` (architecture rules, 09 §2), `.github/**` (workflows, `dependabot.yml`, scripts, `CODEOWNERS` itself), `osv-scanner.toml`, the toolchain and installer pins (S-11), `NOTICE`, the OCR asset directory with its checksum file (S-22), `shared-kernel/**` (09 §2), the licence and governance files (`LICENSE`, `LICENSES/`, `REUSE.toml`, `CLA.md`, `docs/cla-signatures.md`, `.gitleaks.toml`, `docs/dependency-pins.md`, the requirements files of S-36) and the Fan Kit logo files → review by the maintainer mandatory for every pull request that is not his own (S-28) |
| S-6 | Dependencies that cannot be audited or that carry an advisory (if unavoidable) only with an **explicit justification** in the machine-readable field of their entry: a `cargo-vet` exemption with its `notes`, a `deny.toml` `skip` or `ignore` entry with its `reason` (for example `{ id = "…", reason = "…" }`), never in a TOML comment: configuration files carry no comments. The entry also gets a row in the suppression register (09 §3a), with an expiry or revisit date. **Bootstrap (decided 2026-10-13, @greluc):** `cargo-vet` starts by importing the audits of the sources named in the pull request (for example Google, Mozilla, Embark, the Bytecode Alliance); the crates that no import covers get exemptions that all carry the same `notes` text ("initial adoption, not yet audited") and are covered by one shared row in the suppression register with the revisit date 2027-04-13, before release 1.0. The set of exempted crates only shrinks; a new dependency is audited or imported, never added to the bootstrap exemptions. | Review |

### 2.2 Updates (T2)

| ID | Measure | Implementation |
|---|---|---|
| S-7 | **Cooldown period for new versions:** Dependabot proposes version updates no earlier than **7 days** after publication. Experience shows that compromised releases are often discovered within days. **Security updates** are exempt from this. | `.github/dependabot.yml`: `cooldown: default-days: 7` (if not specified, the GitHub docs state a default of 3 days); ecosystems `cargo` and `github-actions` (that the cooldown applies to `cargo` is checked in M0) |
| S-8 | Updates individually or in small groups, never auto-merged; every update updates the lockfile **and** the `cargo-vet` files in the same PR (Dependabot cannot do the audits itself → manual follow-up commit) | Review checklist in 09 §11 extended |
| S-9 | For every update, briefly check: changelog, new transitive crates (diff in `Cargo.lock`), a new or changed build script or procedural macro, new owners on crates.io? | PR template |

### 2.3 Build tools (T4, T6, T14)

| ID | Measure | Implementation |
|---|---|---|
| S-10 | **Withdrawn (2026-10-12).** Secure the Gradle wrapper. There is no wrapper in a Cargo project; its counterpart, a pinned and verified build tool, is the toolchain pin and installer tool pins of S-11 and the Cargo configuration guard of S-4. | – |
| S-11 | **Build toolchain and installer tools pinned and verified:** the Rust toolchain that builds the release is the one in `rust-toolchain.toml` (an exact version, edition 2024; ADR-0005 D10), installed through `rustup` from the official distribution channel; how CI obtains `rustup` itself (runner image or a checksum-verified installer) is verified in M0. The release build jobs (S-14) log `ImageOS`/`ImageVersion` and the tool versions and fail if WiX is not the expected version. A build or CI tool that is not on the image is installed only at a fixed version with a verified checksum, as a documented S-1 exception for build tools: the OSV-Scanner binary (S-19) and the CI tools of S-36. | `rust-toolchain.toml`; workflow steps; `docs/dependency-pins.md` rows for the toolchain, `cargo-packager` and WiX (CODEOWNERS) |
| S-12 | **No code from the network at build time, and a reviewed list of build-time code.** Our own crates have no `build.rs` that accesses the network or runs a downloaded binary. The release build fetches with `cargo fetch --locked` first and builds with network access off where the runner allows it (verified in M0), so a build script cannot download anything unnoticed. **Downloads outside the build** (e.g. a toolchain, an ONNX Runtime archive or an installer tool fetched in a working session for a spike) are never committed and are verified like build inputs before anything from them runs: a PGP signature checked against a key whose fingerprint is confirmed from a second, independent source, or a SHA-256 from a source other than the download host. A `.sha1`/`.md5` next to the artifact only detects transport errors. The ONNX Runtime library comes only from the pinned official release asset (S-22), never from an unpinned download.

### 2.6 Repository and process

| ID | Measure |
|---|---|
| S-28 | Branch protection for `main`: pull request required, required checks green (CI, the DCO check, the licence gate and `reuse lint`, `cargo-vet`, gitleaks, workflow linting), no force push, no deletion; 2FA for all maintainers. CODEOWNERS requests the project owner's review on every pull request. With a single maintainer, a mandatory code-owner review would block his own pull requests, so the project owner may bypass the protection for his own pull requests (decided 2026-10-08); every other pull request needs his review. Merge methods: merge commit or rebase merge; squash merging is off, so the separate lockfile and audit-metadata commits (S-3, S-5) reach `main` unchanged. These are repository settings that the project owner changes on GitHub. |
| S-29 | **Few dependencies** (09 §9): every new dependency needs a justification, a licence check against the licence policy in CLAUDE.md "Stack rules" (ADR-0003, amended by ADR-0005 D9; enforced by S-34) and a look at its maintenance status. Who publishes it on crates.io, and how many owners? Does it bring a build script, a procedural macro, `unsafe` code or native code (S-12; native code only as a registered exception, 09 §3b)? A pure-Rust crate in wide use is preferred to a native binding (ADR-0005 D1). |
| S-30 | **Reproducibility:** the release is built with the pinned toolchain, `--locked` and the same inputs; whether the Rust binary is bit-for-bit reproducible across runners (path remapping, timestamps in the Windows PE header and embedded resources) is checked in the M1 spike and the result is recorded here. Archives built by `xtask` use fixed ordering, timestamps and modes, with the launcher and the runtime binaries executable; the packaged-app smoke test (04 M1) asserts that the binary is executable. Honestly: the installers (MSI/deb) built by the packager are not expected to be bit-for-bit reproducible; the attestation (S-16) partially compensates for this. |
| S-31 | Security reports: `.github/SECURITY.md` with GitHub private vulnerability reporting (enabled) as the channel and the project contact address `lucas.greuloch@gmail.com` as a fallback, response targets (acknowledgement within 7 days, triage within 14 days, a fix in `main` for High and Critical issues within 90 days, coordinated disclosure within 14 days of the fixed release) and the scope; a confirmed report starts a security release ([release-process.md](../release-process.md)) |

### 2.7 Repository hygiene and licence compliance (T6, T11–T13; ADR-0003)

| ID | Measure | Implementation |

| S-32 | **Secret scanning:** gitleaks scans every push and pull request with `.gitleaks.toml` (the default rules plus rules for the UEX secret key and for bearer tokens). A finding blocks the merge. | S-35 | **Licence of every file (REUSE 3.3):** every source file carries an SPDX copyright line and an SPDX licence-identifier line in its header (the one comment the no-comments rule keeps); files that cannot carry one (images, models, jars, generated and vendored files, configuration files under the no-comments rule such as `Cargo.toml` and `deny.toml`) are annotated in `REUSE.toml`; every licence used has its text under `LICENSES/`. `reuse lint` runs in CI on every pull request and push and blocks the merge; an `xtask` header check covers the Rust files before `reuse lint` does. ## 3. What this achieves in practice

| Threat | Covered by | Residual risk |
|---|---|---|
| T1 tampered artifact | S-3, S-4 (checksum for every crate in the lockfile, vendor hashes) | low |

| T3 typosquatting/confusion | S-1, S-2, S-5 | low |
