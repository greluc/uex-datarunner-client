# Supply Chain Security

> **Doc type:** Living spec — binding. Last reviewed: 2026-10-14.

Goal: Neither a compromised dependency, a tampered build tool or CI action, nor a subverted release artifact should bring code onto users' machines unnoticed. The client handles a UEX secret key and runs alongside the game – a compromised build would be a direct attack on the users.

**Honest limit:** Supply chain security is risk reduction, not a guarantee. The following measures primarily prevent *unnoticed* changes (tampered artifacts, re-pointed tags, silently bumped versions). Against a maintainer who publishes a malicious version, only a cooldown period, review, audits and a small number of dependencies help. crates.io publishes no signatures, so authenticity of a crate rests on its checksum in `Cargo.lock`, the audits of S-4 and the review of S-5, not on a signing key.

Amended 2026-10-12: the measures were re-expressed for Cargo after the move from Java 27, JavaFX and Gradle to Rust and egui ([ADR-0005](../adr/0005-rust-and-egui.md), D8). Measure IDs are unchanged; a Gradle-specific measure without a Rust counterpart is marked `Withdrawn (2026-10-12)` and keeps its row. Tools and crates that this document names without a version are chosen and verified at source in M0.

## 1. Threat model

| # | Attack vector | Example |
|---|---|---|
| T1 | Tampered or replaced artifact in the registry or in transit | A crate archive is replaced after publication; a mirror delivers different bytes |
| T2 | Malicious **new version** of a genuine dependency (maintainer account takeover) | Patch release with malicious code is adopted automatically |
| T3 | Typosquatting or dependency confusion via additional sources | A crate with the same name pulled from a git URL, an alternative registry or a `[patch]` entry |
| T4 | Tampered **Rust toolchain** or Cargo configuration | Modified `rust-toolchain.toml`, a `.cargo/config.toml` that redirects the registry or sets `RUSTC_WRAPPER`, a toolchain from an unofficial channel |
| T5 | Compromised **GitHub Action** (tag is re-pointed to a malicious commit) | Incident involving `tj-actions/changed-files` (March 2025) |
| T6 | Tampered **binary assets and build tools**: ONNX models, the ONNX Runtime library, the build's Rust toolchain, installer tooling (`cargo-packager`, WiX, `dpkg-deb`/`fakeroot`), CI tools (OSV-Scanner, gitleaks, actionlint, zizmor, `reuse`, `cargo-deny`, `cargo-vet`) | Replaced model from Hugging Face; ONNX Runtime fetched from an unpinned host; modified WiX on the build machine |
| T7 | Tampering **after** the build (release files replaced) | Installer in the release is swapped |
| T8 | Native libraries that are loaded from a **writable or shared location** (DLL/SO planting) | The ONNX Runtime library found through the current directory or a shared temp directory instead of the installation directory |
| T9 | Runtime loading of code or models from unversioned sources | Model download "latest"; auto-update without signature verification |
| T10 | Optional AI models via Ollama (downloaded by the user) | Tampered model in a third-party registry |
| T11 | Secret committed to the repository or exposed in CI | UEX key in a test fixture, a recorded response or a log |
| T12 | Unsafe workflow | Template injection through a pull-request title; excessive token permissions; an unpinned tool download |
| T13 | Licence contamination or missing notices | A GPL-incompatible shipped dependency; a release without the ONNX Runtime notices or the source archives |
| T14 | Code that runs **at build time** from a dependency: `build.rs` scripts and procedural macros | A build script that downloads and executes a binary, reads secrets from the environment or patches other crates |

## 2. Measures

### 2.1 Resolving dependencies (T1–T3)

| ID | Measure | Implementation |
|---|---|---|
| S-1 | **Only one registry:** crates.io for libraries and build tools that are crates. No git dependencies, no path dependencies outside the workspace, no alternative registries, no `[patch]` or `[replace]` sections, no `mavenLocal`-style local overrides. **Recorded exceptions:** (1) CI tools outside Cargo (S-36: GitHub releases, PyPI); (2) the ONNX Runtime library and, if the crate fetches it from a host of its own, that host: how the library reaches the build is decided in M0 (O-108) so that it is pinned by SHA-256 (S-22); a fetch that is not checksum-pinned is not allowed. Decided by the M0 spike on 2026-10-14 (§2.5): the official release asset on GitHub, fetched by a reviewed step and checked against its pinned SHA-256; `ort` fetches nothing and no crate-side host is used; (3) the installer tooling of S-11 (WiX release asset). | `deny.toml`: `[sources]` with `unknown-registry = "deny"`, `unknown-git = "deny"`, an empty allow-list except crates.io; `[bans] wildcards = "deny"`. The CI guard of S-4 rejects `[patch]`, `[replace]`, `[source]` or `[registries]` entries and `registry`/`git`/`path`-outside-workspace dependency keys in any `Cargo.toml` or `.cargo/config.toml` |
| S-2 | **Only fixed versions:** every dependency is declared once in `[workspace.dependencies]` of the root `Cargo.toml`; no wildcard (`*`) requirements, no git branches or revisions, no pre-release versions. **Recorded exception:** `ort` as a release candidate, pinned exactly (`=2.0.0-rc.14`; ADR-0005 D2, 09 §3b). The Rust toolchain is pinned to an exact version in `rust-toolchain.toml` (never `stable`). Whether further requirements use the exact `=` form or the default caret form is decided in M0; the lockfile (S-3) is what freezes the resolved versions either way. | `cargo-deny` `wildcards = "deny"` and a check in the `xtask` that every member crate inherits its dependencies from `[workspace.dependencies]`; the CI guard of S-4 rejects a pre-release version outside the recorded exception |
| S-3 | **Dependency locking:** the root `Cargo.lock` is committed and covers libraries, build scripts, procedural macros, dev-dependencies and the `xtask` and tool crates of the one workspace, so there is no separate "buildscript" or "settings" classpath. Every CI invocation of cargo passes `--locked` (and `--frozen` where nothing may be fetched); a build whose lockfile would change fails. Transitive versions are frozen. Changes only via `cargo update -p` or `cargo add` in a separate commit. A separate workspace (for example a fuzzing crate) has its own committed lockfile under the same rules. | `.github/workflows/`, the CI guard of S-4; Dependabot's lockfile changes are reviewed per S-8 |
| S-4 | **Checksum verification and audits:** Cargo records a SHA-256 `checksum` in `Cargo.lock` for every registry package and verifies every download against it; `cargo vendor` output is verified against the same checksums and a committed per-package hash list (decided 2026-10-13, O-120: the vendored tree is regenerated in CI and compared with the committed hash list, not committed; measured 2026-10-13, the planned dependency set vendors to 555 to 572 crates, about 608 to 719 MiB on disk and 91 to 99 MiB compressed, against about 3 MB of checksum data). **Authenticity** cannot come from signatures, because crates.io has none: it comes from `cargo-vet` audits (the `supply-chain/` files are committed; imports only from audit sources named in the pull request, exemptions only with a `notes` entry that justifies them, S-6) and from the review of S-5. **PGP verification of artifacts is withdrawn** (no Rust counterpart); the CI guard and audits replace it. | `cargo vet` in CI, blocking; `cargo deny check sources` and `cargo deny check bans`.<br/>• **CI guard** (runs before the first cargo call, like S-12): every CI cargo invocation passes `--locked`. The job fails if any of the following holds:<br/>• `Cargo.lock` has a `[[package]]` with a `source` but no `checksum`, or a `source` other than the crates.io registry;<br/>• a `Cargo.toml`, a `.cargo/config.toml`, `rust-toolchain.toml` or any file under `.github/**` contains `[patch]`, `[replace]`, `[source]`, `[registries]`, a `registry`/`git` dependency key, a `RUSTC_WRAPPER`, `CARGO_REGISTRIES_*`, `CARGO_SOURCE_*` or `CARGO_NET_GIT_FETCH_WITH_CLI` override, or `--locked` is dropped from a cargo call;<br/>• `rust-toolchain.toml` does not name an exact version;<br/>• a vendored package differs from its recorded hash.<br/>The tagged R-SEC-2 test (M0) checks the same rules. |
| S-5 | **New crates or checksums only with review:** `Cargo.lock` and the `supply-chain/` files are updated in the **same PR as the dependency change, as a separate commit**. The diff shows every new crate, version and checksum. For each new crate the PR documents: purpose, SPDX licence, crates.io owners and last release, the repository it links to (and that it matches), whether it has a build script, procedural macro or native code (S-12, 09 §3b), and its `cargo-vet` status (audit, import or justified exemption, S-6). A crate that changes owners or whose source repository moves is treated as new. | `.github/CODEOWNERS`: `Cargo.toml` and `**/Cargo.toml`, `Cargo.lock`, `.cargo/**`, `rust-toolchain.toml`, `deny.toml`, `clippy.toml`, `supply-chain/**` (audits, config, imports), the vendor hash list (S-4), the build-script review list (S-12), `xtask/**` (architecture rules, 09 §2), `.github/**` (workflows, `dependabot.yml`, scripts, `CODEOWNERS` itself), `osv-scanner.toml`, the toolchain and installer pins (S-11), `NOTICE`, the OCR asset directory with its checksum file (S-22), `shared-kernel/**` (09 §2), the licence and governance files (`LICENSE`, `LICENSES/`, `REUSE.toml`, `CLA.md`, `docs/cla-signatures.md`, `.gitleaks.toml`, `docs/dependency-pins.md`, the requirements files of S-36) and the Fan Kit logo files → review by the maintainer mandatory for every pull request that is not his own (S-28) |
| S-6 | Dependencies that cannot be audited or that carry an advisory (if unavoidable) only with an **explicit justification** in the machine-readable field of their entry: a `cargo-vet` exemption with its `notes`, a `deny.toml` `skip` or `ignore` entry with its `reason` (for example `{ id = "…", reason = "…" }`), never in a TOML comment: configuration files carry no comments. The entry also gets a row in the suppression register (09 §3a), with an expiry or revisit date. **Bootstrap (decided 2026-10-13, @greluc):** `cargo-vet` starts by importing the audits of the sources named in the pull request (for example Google, Mozilla, Embark, the Bytecode Alliance); the crates that no import covers get exemptions that all carry the same `notes` text ("initial adoption, not yet audited") and are covered by one shared row in the suppression register with the revisit date 2027-04-13, before release 1.0. The set of exempted crates only shrinks; a new dependency is audited or imported, never added to the bootstrap exemptions. **Trusted publishers (decided 2026-10-14, @greluc, issue #24):** a crate may also be covered by a `cargo-vet` `[[trusted]]` entry in `supply-chain/audits.toml` for the crates.io account (or GitHub trusted-publishing repository) that published it, when an imported source already trusts that publisher or the publisher is a maintainer of the crate's own project (the `rustls`, `tokio`, `tower`, `tracing`, `futures`, ICU4X, AWS-LC, RustCrypto and `rust-lang` teams); each entry ends one year after it is written. The remaining crates are audited by reading (`cargo vet certify`, `notes` say what was read and by whom), and a crate that cannot be read (`aws-lc-sys`) or is never compiled for the shipped targets gets a justified exemption with its register row. The `[[trusted]]` entries and the audits of the first dependency pull request are listed in `supply-chain/README.md`. | Review |

**Implementation of the S-4 guard and the vendor hash list (2026-10-14, issue #14).** Both are `xtask` tasks.

- `cargo xtask guard` reads `Cargo.lock`, every `Cargo.toml`, every `.cargo/config.toml`, every `rust-toolchain.toml` and every file under `.github/`, and exits non-zero on any finding. It is the first step of `cargo xtask check` and the first step of the CI job after the toolchain install, so a violation fails before the gate runs. Its rules, each with a test tagged R-SEC-1 (R-SEC-3 for the toolchain):
  - `Cargo.lock`: every package with a `source` has a `checksum` and the crates.io registry as its source (git, alternative and sparse registries fail);
  - `Cargo.toml`: no top-level `patch`, `replace`, `source` or `registries`; no dependency with `git`, `registry` or `registry-index`, in `dependencies`, `dev-dependencies`, `build-dependencies`, `target.*` and `workspace.dependencies`; no `path` that is absolute or leaves the workspace;
  - `.cargo/config.toml`: the same four sections, a top-level `paths`, `build.rustc`, `build.rustc-wrapper`, `build.rustc-workspace-wrapper`, `net.git-fetch-with-cli`, and every `[alias]` for a resolving command without `--locked` or `--frozen`;
  - `rust-toolchain.toml`: `channel` is an exact `MAJOR.MINOR.PATCH` version (`stable`, `1.99`, `nightly-…` and pre-releases fail);
  - all of these files and everything under `.github/`: no `RUSTC_WRAPPER`, `RUSTC_WORKSPACE_WRAPPER`, `CARGO_REGISTRIES_*`, `CARGO_SOURCE_*` or `CARGO_NET_GIT_FETCH_WITH_CLI`; under `.github/` also no `[patch]`, `[replace]`, `[source]` or `[registries]` header text;
  - under `.github/`: a `cargo build`, `check`, `clippy`, `doc`, `fetch`, `install`, `llvm-cov`, `metadata`, `mutants`, `nextest`, `package`, `publish`, `run`, `rustc`, `rustdoc`, `test`, `tree`, `vendor` or `bench` (or a short alias of these) without `--locked` or `--frozen` before any `--`, with `\` continuations joined and `&&`, `||`, `;` and `|` ending a command. `cargo xtask` is accepted because its alias in `.cargo/config.toml` carries `--locked`, which the same check enforces.
- The guard fails, and does not skip the file, when a file it selects is not valid UTF-8 or is a symbolic link. Markdown files under `.github/` are prose and are not scanned.
- The `.github/` rules read text, not YAML: a step name that contains the words `cargo build` is read as a command and fails, and a `[source]` in a YAML flow list does too. The compiler-wrapper keys and variables beyond the four of the table above, and the path rule, are stricter than the table's wording on purpose.
- **Bootstrap limit.** `xtask` is built by Cargo before the guard can run, so the guard cannot keep a hostile Cargo configuration from affecting that first build. What protects it is the checksum of every `xtask` dependency in `Cargo.lock`, the review of S-5 and CODEOWNERS on `.cargo/**`, `Cargo.toml`, `Cargo.lock` and `xtask/**`.
- `cargo xtask vendor-hashes write` runs `cargo vendor --locked --versioned-dirs` into `target/xtask-vendor` with `CARGO_HOME` pointing at an empty directory beside it, hashes every package directory, and writes `supply-chain/vendor-hashes.txt`; `cargo xtask vendor-hashes verify` does the same and compares. The tree is deleted afterwards and never committed (O-120). CI runs `verify` on the Windows and the Linux runner, so a platform-dependent vendor tree would show.
- The list has the header line `vendor-hashes 1` and then one line per vendored package, ordered by name and version: `name version archive-sha256 tree-sha256`. The archive hash is the `checksum` of `Cargo.lock`. The tree hash is the SHA-256 over the sorted lines `file-sha256  relative/path` of every file of the package directory except the top-level `.cargo-checksum.json`. `verify` fails on a package that is missing, unexpected, has a different archive checksum (a `Cargo.lock` change without the list) or different files (a tampered crate), and on a vendor directory entry that `Cargo.lock` does not explain.
- Updating a dependency is therefore two commits in one pull request (S-5): the `Cargo.toml` and `Cargo.lock` change, then `cargo xtask vendor-hashes write` and the changed list; the diff of the list shows every new crate, version and checksum.
- Negative tests (M0, R-SEC-1, R-SEC-2): a git, alternative-registry or checksum-less package in `Cargo.lock`, a `git` or `registry` dependency and every forbidden section, key, variable and dropped `--locked` fail the guard; a vendored file that is changed, added or removed, a changed archive checksum, an unlisted package and an unlisted vendor directory fail `verify`; `cargo build --locked` fails against a stale or missing `Cargo.lock` (a real Cargo, offline), and `cargo vendor --locked` fails against a stale one.

**Implementation of the `cargo-vet` bootstrap (2026-10-14, issue #16).** The store is `supply-chain/config.toml`, `audits.toml` and `imports.lock`; the procedure for adding or updating a dependency is in `supply-chain/README.md`.

- **Version.** `cargo-vet` 0.10.2. The project's releases carry binaries only up to 0.10.0, whose parser skips 80 audits of the Bytecode Alliance file ("made with a more recent version of cargo-vet") and writes `imports.lock` differently, so CI installs 0.10.2 from crates.io with `cargo install --locked --version =0.10.2` (S-36, `docs/dependency-pins.md`).
- **Imports named in the pull request.** `bytecode-alliance`, `embark-studios`, `google` and `mozilla`, each from the URL the `cargo-vet` registry lists. On the current dependency set they cover only `quote`; the other 28 crates of `xtask` are exempt. The sources stay because the planned set (egui, `tokio`, `reqwest`, `rusqlite`) is the kind of crates they audit; a further source is a reviewed change of `config.toml`.
- **Bootstrap exemptions.** Each of the 28 carries the `notes` text "initial adoption, not yet audited"; one shared row in the suppression register (09 §3a) covers them with the revisit date 2027-04-13. `supply-chain/bootstrap-exemptions.txt` lists the exempted crates.
- **Rule in the check suite.** `cargo xtask check` has a step "cargo-vet exemptions" (tests tagged R-SEC-2, no network, no `cargo-vet` binary): every exemption with the bootstrap text must be a crate of the baseline file, every crate of the baseline file must still be exempt, a bootstrap exemption certifies exactly `safe-to-deploy`, so the set cannot grow and a removal shows in the diff; any other exemption needs non-empty `notes` and a register row of its own with a revisit date; the shared row exists exactly while bootstrap exemptions do and ends with 2027-04-13. The baseline only shrinks by review: CODEOWNERS covers `supply-chain/**`, and a line added to the baseline violates S-6.
- **CI.** The job `vet` of `.github/workflows/ci.yml` installs `cargo-vet` with `cargo install --locked --version =0.10.2` after the guard, checks the reported version and runs `cargo vet --locked`, which fetches nothing and fails on a crate that is neither audited, nor imported, nor exempted. It runs on Linux only: the result does not depend on the platform.
- **Tool-written comments.** `cargo vet --locked` rejects a store whose files differ from the tool's own formatting, and that formatting starts each of the three store files with a one-line header comment. These three comments are the only ones kept in `supply-chain/`; they are written by the tool and not edited by hand.

### 2.2 Updates (T2)

| ID | Measure | Implementation |
|---|---|---|
| S-7 | **Cooldown period for new versions:** Dependabot proposes version updates no earlier than **7 days** after publication. Experience shows that compromised releases are often discovered within days. **Security updates** are exempt from this. | `.github/dependabot.yml`: `cooldown: default-days: 7` (if not specified, the GitHub docs state a default of 3 days); ecosystems `cargo` and `github-actions` (that the cooldown applies to `cargo` is checked in M0) |
| S-8 | Updates individually or in small groups, never auto-merged; every update updates the lockfile **and** the `cargo-vet` files in the same PR (Dependabot cannot do the audits itself → manual follow-up commit) | Review checklist in 09 §11 extended |
| S-9 | For every update, briefly check: changelog, new transitive crates (diff in `Cargo.lock`), a new or changed build script or procedural macro, new owners on crates.io? | PR template |

**Implementation of Dependabot (2026-10-14, issue #16).** `.github/dependabot.yml` and the `dependabot` step of `cargo xtask check` (module `dependabot`, tests tagged R-SEC-5).

- **Configuration.** The ecosystems `cargo` and `github-actions` for `/`, weekly on Mondays, `cooldown: default-days: 7`, `open-pull-requests-limit: 5`, the maintainer as assignee, commit prefixes `build(deps)` and `ci(deps)` (Dependabot capitalises the summary after the prefix, which the Conventional Commits rule of CONTRIBUTING.md otherwise forbids; the pull request keeps its commits as Dependabot wrote them). There are no groups: every update is its own pull request (S-8).
- **Cooldown verified.** GitHub's options reference lists Cargo and GitHub Actions among the ecosystems that support `cooldown` with `default-days` (checked 2026-10-14; the question left open in S-7). The first Dependabot pull request is the practical confirmation.
- **Never auto-merged.** Dependabot itself merges nothing. The step fails when an ecosystem has no `cooldown`, when `default-days` or any `semver-*-days` is below seven, when the cooldown has an `exclude` key (in block or flow style), when either required ecosystem is missing, or when a non-Markdown file under `.github/` mentions `gh pr merge`, `automerge`, `auto-merge` or `fetch-metadata`.
- **What Dependabot cannot do** (S-8): it changes `Cargo.toml` and `Cargo.lock` only. Its pull request is red on the vendor hash check and on `cargo vet` until a maintainer adds the vendor hash commit and the audit, import or exemption move from `supply-chain/README.md`. It does not update the pins of `docs/dependency-pins.md` that are not actions, nor the toolchain.
- **Action pins without a version comment.** Dependabot normally reads the tag from a comment behind the SHA. Whether it proposes SHA updates for a pin without one is not verified; the first action update pull request settles it, and a pin it ignores is moved by hand with its row in `docs/dependency-pins.md`.

**Downloads outside the build** (e.g. a toolchain, an ONNX Runtime archive or an installer tool fetched in a working session for a spike) are never committed and are verified like build inputs before anything from them runs: a PGP signature checked against a key whose fingerprint is confirmed from a second, independent source, or a SHA-256 from a source other than the download host. A `.sha1`/`.md5` next to the artifact only detects transport errors. The ONNX Runtime library comes only from the pinned official release asset (S-22), never from an unpinned download. Exception (O-127, decided 2026-10-14): the SHA-256 of the ONNX Runtime library may rest on the official GitHub release of `microsoft/onnxruntime` alone; where a second source exists (a signed NuGet package of the same version, an Authenticode signature), `docs/dependency-pins.md` records it.

### 2.4 CI/CD (T5, T7)

| ID | Measure | Implementation |
|---|---|---|
| S-13 | **Pin actions by full commit SHA**, never by tag or branch, and **without a trailing version comment** (configuration files carry no comments). The tag each SHA resolves to is recorded in `docs/dependency-pins.md` (action, tag, SHA, date checked, where used); a PR that moves a pin updates its row after checking that the tag resolves to the SHA. An action counts as pinned only when the code it runs is pinned. Actions that run a container image by tag (`runs.using: docker` with `docker://…:<tag>`, e.g. `google/osv-scanner-action`) are not used, and tool binaries that a workflow downloads are pinned by SHA-256 (S-19, S-36). | `uses: actions/checkout@<40-hex-sha>`; Dependabot (`github-actions`) proposes SHA updates after the S-7 cooldown, and the PR updates the row in `docs/dependency-pins.md` |
| S-14 | **Minimal permissions, separated duties:** `permissions: contents: read` as the workflow default. Write permissions and secrets only in jobs that do not run the build:<br/>• **Release:** a build matrix (`windows-latest`, `ubuntu-latest`) with `contents: read`, `actions/checkout` with `persist-credentials: false` and no secrets runs `cargo build --locked --release`, the packaging (`cargo-packager`, `xtask` archives), the SBOM (S-18) and the packaged-app smoke test, and uploads the outputs with `actions/upload-artifact`. A separate `publish` job (`needs` the build; environment "release", S-15) never checks out or builds the code. **Implementation of the OSV gate (2026-10-14, issue #16).** The gate script of S-19 is the `xtask` task `cargo xtask osv-gate <report.json>`, not a file under `.github/scripts/`, because our own code is Rust only and `xtask` is where CODEOWNERS and the architecture rules already apply (ADR-0005 D12).

- **Input.** The JSON that `osv-scanner scan source --format json --output-file <report.json> --no-call-analysis rust --lockfile Cargo.lock` writes. Call analysis is switched off, because OSV-Scanner's Rust call analysis runs build scripts. `Cargo.lock` is the only file scanned, so every package of the report must be of the ecosystem `crates.io`; any other ecosystem fails the gate.
- **Shipped graph.** `cargo metadata --locked --no-deps` lists the workspace members; every member is shipped except `xtask` and the members under the workspace's `tools/` directory. For each shipped member and for each of `x86_64-pc-windows-msvc` and `x86_64-unknown-linux-gnu`, `cargo tree --locked --package <member> --target <target> --edges normal --all-features --prefix none --format "{p}"` names the packages. Build dependencies and dev-dependencies are not in this set (S-19: normal dependencies of the shipped binaries), all features are, because the set may only err towards blocking. Until the first crate other than `xtask` exists the set is empty and every finding is only reported; the first ticket that adds a shipped crate makes the gate bite without a change to it.
- **Verdict.** A group of vulnerability records of a shipped package blocks when its `max_severity` is 7.0 or more or is missing or unreadable (fail closed until triaged). A record that no group names counts as an unscored group, so a report cannot hide a record by omitting its group. A score outside 0.0 to 10.0 counts as no score. RUSTSEC notices without a CVSS score (unmaintained, unsound) are unscored groups and therefore block a shipped package until triaged, which is stricter than `cargo-audit` and `deny.toml`; the first such false block is settled in `osv-scanner.toml`. A report that is not JSON, has no `results` array or names a package without name, version or ecosystem fails the gate. Findings of tooling packages and shipped findings below 7.0 are printed as `reported:`.
- **Tests.** Tagged R-SEC-5, over the recorded reports in `xtask/fixtures/osv/` (a trimmed real run of OSV-Scanner 2.6.0 on a lockfile with `smallvec 0.6.9` and `time 0.1.43`, and the clean report) and over reports built in the tests: blocking and non-blocking severities, the limit itself, missing and unreadable scores, a record without a group, tooling-only findings, another version of a shipped package, malformed reports, and the selection of the shipped members.
- **CI.** `.github/workflows/advisories.yml` runs on every pull request, on every push to `main` and daily at 04:23 UTC on the default branch (`contents: read`, no secrets, no SARIF upload). Three jobs, each with a pinned tool (`docs/dependency-pins.md`):
  - `cargo-audit` 0.22.2 audits `Cargo.lock` against the RustSec database and fails on a vulnerability; unmaintained, unsound and yanked notices are printed and do not fail it.
  - `cargo-deny-advisories` runs `cargo deny --locked check advisories` with the `[advisories]` section of `deny.toml` (`yanked = "deny"`, `unmaintained` and `unsound` `none`, no `ignore` entry): a vulnerability or a yanked crate fails it.
  - `osv-scanner` 2.6.0 scans `Cargo.lock`, then `cargo xtask osv-gate` judges the report. The job accepts the scanner's exit code 0 and 1 (findings) and fails on any other, so a scanner that cannot run does not pass.
- **Corrections to the table row of S-19 (2026-10-14).** (1) `cargo-audit` blocks on a vulnerability in any package of `Cargo.lock`, tooling included, because the acceptance criteria of issue #16 require it to block and it cannot tell shipped from tooling packages; the report-only clause of S-19 is withdrawn, the confirmation promised for M0 is this one. (2) The gate script is the `xtask` task above, not a file under `.github/scripts/`. (3) The daily scan of the latest release tag does not exist yet: there is no release; it is added to the release workflow when the first release is built (R-SEC-5, release-process.md).
- **Seeded failures (2026-10-14).** `cargo-audit` exits 1 with four vulnerabilities on a lockfile with `smallvec` 0.6.9 and `time` 0.1.43; `cargo deny check advisories` fails with RUSTSEC-2020-0071 on a scratch project that depends on `time` 0.1.43; OSV-Scanner 2.6.0 reported those two packages and exited 1, which is where the fixtures come from. The tests of the gate cover the blocking path, because no shipped crate exists to block yet.

- **Exceptions.** OSV-Scanner reads `osv-scanner.toml` next to the scanned lockfile. The file does not exist; an `[[IgnoredVulns]]` entry needs `id`, `reason` and `ignoreUntil` and a row in the suppression register (09 §3a), as S-19 says. `cargo xtask check` does not yet read that file, so the review of CODEOWNERS (S-5) is what stands behind it until the first exception is needed.

**Implementation of the `cargo-deny` gate for licences, sources and bans (2026-10-14, issue #15).** `deny.toml` at the repository root configures it; `cargo xtask check` runs `cargo deny --locked check licenses sources bans` as its second step, after the supply-chain guard, and the CI job installs the pinned release binary on both runners (S-36, `docs/dependency-pins.md`).

- **Licences.** The allow-list is the licence policy of CLAUDE.md "Stack rules" with the five additions of D9 and O-117. EPL is not on it, because `cargo-deny` cannot see whether a GPL Secondary License is designated; an EPL crate needs a per-crate `exceptions` entry with its register row. MPL-2.0 is allowed as a licence, and the "Incompatible With Secondary Licenses" notice is read per crate when the crate is added (S-5). `unused-allowed-license` is `allow`, because the list names licences that no current crate uses. A crate with missing or ambiguous licence data fails as `unlicensed`.
- **Sources.** Only the crates.io index is allowed; `unknown-registry` and `unknown-git` are `deny`, and there is no `allow-git` or `allow-org` entry.
- **Bans.** `wildcards` is `deny`, with `allow-wildcard-paths` so that the path dependencies between the workspace's private crates need no version, and `multiple-versions` is `deny`: a second version of a crate needs a `skip` entry with a `reason` and a register row. A wildcard requirement on a crates.io dependency is pinned by a test of the configuration and not by a fixture, because a fixture would need the network (`cargo-deny` exempts a path dependency with `version = "*"`).
- **Graph.** The targets are `x86_64-pc-windows-msvc` and `x86_64-unknown-linux-gnu`, dev-dependencies are excluded. The workspace holds only `xtask` so far, so the graph is `xtask` and its dependencies. `--exclude-unpublished` is not used, because every workspace member is `publish = false` and the graph would be empty; narrowing the gate to the crates of the shipped binary is part of the first ticket that adds one.
- **Suppressions.** Corrected 2026-10-14 (issue #16): the `advisories` check is configured (`yanked = "deny"`, `unmaintained` and `unsound` `none`, `ignore = []`) and runs in `advisories.yml`, not in `cargo xtask check`, because it fetches the RustSec database (see the S-19 implementation note). A `skip`, `skip-tree`, `ignore`, licence `exceptions` or `clarify` entry is checked by `cargo xtask check` (`xtask/src/deny.rs`): it needs a non-empty `reason` where the key has the field, and a row in the suppression register (09 §3a) that names `deny.toml` and the entry in backticks and ends with a revisit date. None exists today.
- **Negative tests (M0, R-SEC-10, R-SEC-1).** The `xtask` tests run the real `cargo-deny` with the repository's `deny.toml` against fixture projects: a dependency under each of AGPL-3.0-only, GPL-3.0-only, GPL-2.0-only, BSD-4-Clause, EPL-2.0, CDDL-1.0 and SSPL-1.0 fails as `rejected`; a dependency without licence data fails as `unlicensed`; `MIT AND GPL-3.0-only` fails and `MIT OR GPL-3.0-only` passes; a dependency under each allowed licence passes; a git dependency fails as `source-not-allowed`; two versions of one crate fail as `duplicate`. The tests fail, and are not skipped, when `cargo-deny` is not on the `PATH`.

**Implementation of the repository gates for licences, sign-offs and language (2026-10-14, issue #17).** Three steps of `cargo xtask check` and one task run the rules; `reuse lint` and the DCO check have their own jobs in `.github/workflows/repository-gates.yml`.

- **Header check (S-35).** The `source headers` step (module `header`) reads every `.rs` file that Git tracks or would track (`git ls-files --cached --others --exclude-standard`, module `tracked`) and requires one or more SPDX copyright-text lines (`YYYY` or `YYYY-YYYY`, then a holder) directly followed by an SPDX licence-identifier line holding an expression that parses: identifiers joined by `AND`, `OR` and `WITH`, with balanced parentheses. Any holder and any expression are accepted, because ported code keeps its upstream notice (CLAUDE.md "Working rules"); `reuse lint` checks that the licence text exists under `LICENSES/`. The module's own source builds the two tag strings with `concat!`, because `reuse` reads a tag name followed by its colon anywhere in a file, in a string or a doc comment, as that file's licence information.
- **Licence copy (S-35).** The `licence copy` step compares `LICENSE` and `LICENSES/GPL-3.0-or-later.txt` byte for byte (module `licence`) and fails with the offset of the first difference; an empty `LICENSE` fails too. `.gitattributes` fixes the line endings of both to LF.
- **`reuse lint` (S-35).** The job `reuse` installs `reuse` 6.2.0 from two hash-locked requirements files into a throwaway virtual environment (S-36): `.github/requirements/reuse-build.txt` holds the build backend (`poetry-core`, installed from wheels first), and `.github/requirements/reuse.txt` holds `reuse` and every transitive package. `reuse` 6.2.0 publishes a source distribution and one wheel for CPython 3.10 against glibc 2.41, so the second install builds the source distribution without build isolation (`--no-build-isolation`) against the already installed backend; the file lists only the hash of the source distribution. The optional `charset-normalizer` dependency is locked as well, because `reuse` needs one encoding detector and does not start without it. The files were compiled for CPython 3.12 and `manylinux_2_28` with a 7-day cooldown (cut-off 2026-10-07), so the job runs on `ubuntu-24.04` instead of the floating `ubuntu-latest` and fails if `python3` is not 3.12 (moving to a newer image means recompiling both files); the install was run in an `ubuntu:24.04` container (Python 3.12.3, no `libmagic`) before the pin was recorded. A bump of `reuse` regenerates both files in a reviewed pull request (S-8, S-9).
- **DCO check.** `cargo xtask dco <base> <head>` (module `dco`) runs `git log --format=… <base>..<head>` and requires on every non-merge commit a `Signed-off-by: Name <address>` line in the last paragraph of the message (the trailer block), starting in the first column, so a quoted or indented line does not count, whose name equals the author name and whose address equals the author address, ignoring case; a GitHub noreply address matches with and without its numeric prefix. An empty range fails, because a mistyped range must not pass. The job `dco` runs on pull requests only, with a full-history checkout and the base and head commits of the pull request. Bot commits are not exempt, since an author name is free text: a Dependabot commit passes only if its sign-off matches, and the maintainer re-signs it with the lockfile follow-up commits (S-8).
- **English check (CLAUDE.md "Language", ADR-0005 D12).** The `english` step (module `english`) reads every tracked UTF-8 file and fails on a line with a German umlaut or the German sharp s or with two distinct words of a list of German function words that are not English words (the list is in the module's source). The exceptions are in `xtask/english-allowlist.toml`: `[[exception]]` tables with a `path` (a file, or a directory ending in `/`) and a mandatory `reason`; an entry that excuses no German line fails the check, so the list cannot go stale. It replaces the TSV file planned in 09 §3.
- **Header placement for other file types (O-40).** Rust files carry the header, enforced by the header check. Formats with a comment syntax that hold source (shell scripts, SVG, XML, HTML) carry the same two lines as the first comment, after a shebang or an XML declaration. Everything else, and every file under the no-comments rule or without a comment syntax (TOML, YAML, JSON, message catalogues whose format has no comments, generated files, images, models), is annotated in `REUSE.toml`; there are no `.license` side files, so there is one place to look.
- **Seeded failures (2026-10-14).** A throwaway Rust file without header, a one-byte change to `LICENSES/GPL-3.0-or-later.txt` and a German sentence in a Markdown file each failed exactly their own step of `cargo xtask check`; a Rust file with a header missing its licence-identifier line and an unsigned commit are covered by tests, the latter against a real `git log` in a scratch repository.
