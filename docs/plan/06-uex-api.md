Answered 2026-10-25 [UEX]: **`api.uexcorp.uk` is the primary host**, because it is not behind Cloudflare's challenge, so non-browser clients such as desktop apps and CI runners are not challenged there. `api.uexcorp.space` serves the same API and accepts writes too, but sits behind the challenge, and UEX asks desktop clients **not to use it as a fallback**. [UEX]: the secret key is what authorises a report; the app token only identifies the client. [UEX follow-up]: until 2026-10-25 the server ignored the header, which mattered only for tokens with the lock enabled; it is now read, and the lock works as documented. ## Submitting: `POST /data_submit`

Documentation slug: `post_data_submit`. Bearer token and `secret-key` header.

```json
{
  "id_terminal": 89,
  "type": "commodity",
  "is_production": 0,
  "game_version": "4.10.1",
  "faction_affinity": 15,
  "date_added": 1791500000,
  "screenshot": "<base64 png/jpg>",
  "details": "optional",
  "prices": [
    {"id_commodity": 1, "price_sell": 120, "scu_sell": 593, "status_sell": 2},
    {"id_commodity": 24, "price_buy": 136, "scu_buy": 529, "status_buy": 2, "container_sizes": "1,2,4,8,16"}
  ]
}
```

Corrected 2026-10-26 [UEX]: `container_sizes` belongs to the row, not to the report (see below); the example above follows the server.

Report level [DOC]:

- Required: `id_terminal`, `type` (`commodity | item | vehicle_buy | vehicle_rent`), `is_production` (1 production, 0 testing), `prices[]`.
- `game_version` string|null; **defaults to the LIVE version** when omitted. Only the current LIVE or PTU version is accepted (`invalid_game_version`: "game version does not exist. LIVE or PTU accepted only"). [UEX]: exactly `data_parameters.global.game_version` for LIVE, or exactly `global.game_version_ptu` while `is_accepting_ptu_reports` is 1; once LIVE moves to a new version, the previous one is rejected with `invalid_game_version`, with no grace period (A18 refuted). The version sent is the one `data_parameters` names, whatever the launcher calls the build; EPTU and Tech-Preview builds count only when their version equals `game_version_ptu` (A9, points 13 and 21).
- `container_sizes` string|null: CSV subset of {1,2,4,8,16,24,32}. [DOC] showed it per report. Corrected 2026-10-26 [UEX]: the server reads it **per row**, as `prices[n].container_sizes` (a CSV string such as `"1,2,4,8,16,32"`); a top-level `container_sizes` is ignored, and the documentation now shows the row field. A row without it keeps the sizes already on record for that commodity at that terminal, so UEX asks to send it only where the player actually read it. The client sends each row's own set when it passes I2, and leaves the field out of every other row (R-OCR-9; decided 2026-10-26, O-136, superseding the one-report-per-set split of O-92).
- `faction_affinity` int, −100..100, only for `commodity` and `item`: the reporter's affinity with the faction that runs the terminal (point 27). The client sends it only when the user entered it (R-SUB-13; decided 2026-10-09, O-93). [UEX]: the player's own affinity with that faction; the terminal does not show it, the player knows it from their reputation; optional, defaults to 0, and ignored at terminals with `is_affinity_influenceable` = 0; UEX has no published model of how far it moves prices.
- `date_added` int|null: "Report date (optional; must be a past date within the last 30 days)"; error `invalid_date` (point 18). The client sends the report's `observedAt` in Unix seconds, and the R-VAL-6 hard limit stays at or below 30 days (decided 2026-10-09, O-91). [UEX]: it must be within the last 30 days and not in the future; it feeds the history, the averages and the price row's `date_modified`, so sending the observation time is right. It does **not** decide the live price: consolidation processes approved reports in submission order (report ID), so the last report submitted sets the live price (R-VAL-8 stays).
- `details` string|null.
- `screenshot` string: png or jpg in base64, "up to 10.00 MB"; "required for new datarunners (90-day evaluation period)"; `screenshot_required` is "primarily applicable to users in the evaluation period or under restrictions"; the error is called `screenshot_length_exceeds_limit`. The client keeps the base64 string at most 10,000,000 bytes long (R-SUB-7; decided 2026-10-09, O-98), which stays inside the limit. [UEX]: the 10 MB limit applies to the **decoded** image; a `data:image/...;base64,` prefix is tolerated; the screenshot requirement is checked in dry runs too, where the image is not uploaded. Stored screenshots are resized to fit 1920×1080 and recompressed, so a tall stitched image may become unreadable for the moderators who review it: "one capture of the terminal per request works best". The client therefore sends one submission per capture, each with that capture's crops (R-SUB-7; decided 2026-10-26, O-137; A11).

Row level for `type = commodity` [DOC]:

- `id_commodity` (required).
- `price_buy` **or** `price_sell` (UEC per SCU; "only one input is allowed"; left empty when `is_missing`).
- `is_missing` int: 1 when the commodity is no longer sold at the terminal. [UEX]: it means "this terminal no longer trades this commodity" and removes the price at consolidation; the API does not reject it next to `scu_*` or `status_*`, but UEX asks to send it "on its own"; `is_missing` reports always go to manual review (point 12).
- `scu_buy` / `scu_sell` int: "inventory amount displayed at terminal" – the number the terminal shows, on either side (A10). [UEX]: a reported 0 is stored as 0, which UEX treats as "not reported"; a row whose status is above 1 (stock present) must carry the SCU too, or the report is declined (point 8).
- `status_buy` / `status_sell` int: 1 (out of stock) to 7 (maximum), see `commodities_status`.
- `container_sizes` string|null: the row's offered container sizes as CSV (see "Report level"; [UEX] 2026-10-25).
- `quality` int|null, 0–1000. Every live price row reports `quality` 0; commodity terminals do not show it.
- **A row carries one side only.** Errors: `has_both_price_buy_and_price_sell`, `has_both_scu_buy_and_scu_sell`, `cannot_have_both_status_buy_and_status_sell`, `cannot_have_both_price_buy_and_status_sell`, `cannot_have_both_price_buy_and_scu_sell`, `cannot_have_both_price_sell_and_status_buy`, `cannot_have_both_price_sell_and_scu_buy`. One payload may mix buy rows and sell rows (the official example does); the plan still sends one report per side (point 14). [UEX]: a terminal never trades both sides of the same commodity, and UEX treats such a pair as an error.
- A row needs a price or `is_missing` (`has_no_prices_and_no_is_missing_set`).

Limits and results:

- At most 500 rows per submission (`max_rows_exceeded`) [DOC].
- `too_many_reports`: more than 1000 reports in the last 30 minutes [DOC]. One UEX report is one row (see `data_info`), so the budget counts rows (point 16). [UEX]: HTTP 429; dry runs are not stored and do not count. Corrected 2026-10-26 [UEX follow-up]: it now counts **only the user's own** reports of that type within the window; the first answer had described a site-wide count over all users.
- `duplicated_report`: "a report for the same item and location has been submitted within the last 5 minutes" [DOC]; observed as HTTP 400 with an empty `message` [3P-OBS]. A removed report no longer blocks a new one (`data_remove`). Corrected 2026-10-26 [UEX follow-up]: it looks only at **the user's own** reports of the same terminal and commodity from the last 5 minutes, ignoring expired ones, like the website; another datarunner's report no longer blocks. Side, `is_production` and LIVE/PTU play no part, so a buy and a sell row of one commodity at one terminal are one key, on purpose (a terminal never trades both sides). The window is compared against the **stored `date_added`**, so a resend of an observation older than 5 minutes is not caught as a duplicate. Dry runs never create a duplicate, but can be rejected because of the user's own real report. The answer carries `data.report` (`id_terminal` and the commodity ID), not the row index (point 11, A12).
- **Row-by-row processing** [UEX]: a request is processed row by row and **stops at the first error**. Rows before it are stored, and the error answer does not list their IDs. Validation errors carry `data.row` (zero-based index into `prices[]`); `duplicated_report` carries `data.report` instead. How the client resolves such an answer is O-138 (R-SUB-9).
- Success output [DOC]: `ids_reports` **string|null**, `date_added` int, `username` string|null. Corrected 2026-10-09: the earlier [3P] notes showed `ids_reports` as an array; the documentation typed it as a string, while real production responses carry an array of numeric strings and `date_added` as a numeric string (see "Observed by third parties"). Answered 2026-10-25 [UEX]: `ids_reports` is an **array of numeric strings in the order of `prices[]`** (`"0"` in a dry run), and the documentation now says so; `date_added` is a Unix timestamp, which the follow-up made **always an integer** (it had come back as a numeric string whenever the client sent one). The parser still accepts both shapes of both fields (R-API-5).
- [RN 2026-08-26]: "Data submissions that fail now tell you which entry was rejected and why, instead of a generic error"; "Data submissions that only partially go through now say so, instead of reporting success." [UEX]: the rejected entry is `data.row` or `data.report`; the stored rows before it are not listed.

**Rows stored before an error** (O-138, open – default applied): UEX processes `prices[]` in order and stops at the first error; the rows before it are stored and their IDs are not returned [UEX]. The client reads an error answer of a submission with several rows like this:

- **The answer names the failing row** (`data.row`, or `data.report` matched to the row with that terminal and commodity), or the code is `database_error` with a row index: the rows before it become unmapped rows of a `PartiallyAccepted` report, resolved through `data_info` as in R-SUB-9; the failing row takes the class of its code; the rows after it were not stored and go back with the failing row's outcome.
- **`database_error` without a row index**, or any unknown-outcome failure: every row is unmapped and resolved through `data_info`.
- **A report-level code without a row** (account, acceptance closed, `screenshot_required`, `invalid_date`, `invalid_game_version`, `terminal_not_found` and the other codes of the "Report" group): nothing was stored. This rests on assumption A25 until UEX confirms that these checks run before the first row (point 30).

The codes of the other report types (`item`, `vehicle_*`) are classified when those types are built (R-SCOPE-2); until then they count as permanent.

## Reading, correcting and withdrawing reports

Added 2026-08-10 [RN]. All three need the Bearer token and the `secret-key` header [DOC].

- **One UEX report is one row** (one terminal, one commodity, one side). A plan `Report` ([11](11-ddd-and-tdd.md) §A1) is one UEX *submission*; its rows become as many UEX reports, each with its own ID ("UEX report ID", 11 §A1) and lifecycle status.
- **Decided 2026-10-09 (O-88, O-89, O-90, O-103):** the history shows each row's lifecycle status, polled from `data_info` at most every 5 minutes (manual refresh at most once a minute) with `limit=100` and the `username` filter, until a final status (`consolidated`, `declined`, `expired`) or 14 days after sending; "accepted" for the local prior update (R-VAL-7) is the `ok` of `data_submit`, and a later `declined` or `expired` reverts it. Rows are mapped to report IDs only after a `data_info` lookup of terminal, commodity and `date_added`. Withdrawal is one `data_remove` per row, offered only while `is_editable` = 1, with a per-row outcome. `data_edit` is not used (R-SUB-10).
- **Lifecycle status** (`data_info.status`): `pending` (waiting for the approval bot), `under_review` (a moderator decides), `queued` (PTU report parked until that version goes live), `approved` (cleared, waiting for consolidation), `consolidated` (folded into the live prices), `declined` (rejected as inconsistent or invalid), `expired` (sat unapproved too long). UEX aims to process reports within 24 hours [TERMS §6.2.5].
- **Report IDs are not unique**: "Report IDs repeat across the table's partitions, so the ID alone does not identify a single row — compare `date_added`." [UEX]: for `data_remove` the ID alone is enough, because it only reaches the user's own reports and resolves to a single row; the client still stores every ID with its `date_added` and maps rows through `data_info` (O-88, O-103).
- **Dry runs are never stored** [UEX]: an `is_production=0` submission runs the same checks as a real one (user, terminal, version, rows, duplicates, screenshot requirement) and stops before anything is stored or uploaded; its IDs come back as `"0"`, and `data_info`, `data_edit` and `data_remove` cannot see it (point 29). A datarunner can remove a real report until it is consolidated; after that it is a moderator action.
- **After a timeout** [UEX]: check what landed with `GET data_info` (filterable by `id_terminal` and `type`) before resending, and do not rely on `duplicated_report` for it, because the duplicate window compares against the stored `date_added` (R-SUB-9).

`GET /data_info` [DOC]:

- Filters: `id`, `type`, `id_terminal`, `status`, `username`, `limit` (1–100, default 50). No time window, no own-only filter (filter by `username`), no paging; order not documented.
- Every datarunner can read every report; removed reports are not listed; only API report types are listed.
- Output per report: `id`, `type`, `status`, `id_user`, `username`, `id_terminal`, `id_commodity`, `id_item`, `id_category`, `id_vehicle`, `name`, `price_buy`, `price_sell`, `price_rent`, `scu_buy`, `scu_sell` ("as reported, not the projected demand"), `status_buy`, `status_sell`, `quality`, `container_sizes`, `faction_affinity`, `details`, `game_version`, `is_missing`, `is_new_item`, `is_new_at_location`, `is_ptu_report`, `is_contested`, `is_owner`, `is_editable` (1 on own reports until they consolidate), `has_attachments`, `has_comments`, and the timestamps `date_added`, `date_modified`, `date_checked`, `date_approved`, `date_declined`, `date_consolidated`, `date_expired`, `date_queued`.
- Codes: `service_unavailable`, `access_denied`, `missing_secret_key`, `invalid_secret_key`, `user_not_found`, `user_disabled`, `user_not_allowed`, `invalid_type`, `invalid_status`, `invalid_limit`, `ok`.

`POST /data_edit` [DOC]:

- Input: `id`, `is_production`, and the **complete** row (`price_buy`/`price_sell`, `is_missing`, `scu_*`, `status_*`, `quality`, `container_sizes`, `faction_affinity`, `details`). **Omitted fields are cleared**, not kept.
- Terminal, type, commodity and game version cannot change. An edit sends the report back to the start of the approval pipeline.
- Own reports only, and only until they consolidate (`report_consolidated`); another user's report answers `report_not_found`.
- Output: `id`, `type`, `is_new_at_location`, `date_modified` (0 when `is_production` is 0).
- Additional codes: `missing_id`, `report_not_found`, `report_consolidated`, `invalid_container_size`.

`DELETE /data_remove/id/{id}/` [DOC]:

- **One report (row) per call.** No `is_production` parameter is documented.
- Own reports only, until they consolidate. Soft delete: the report stops counting, leaves the approval queue and disappears from `data_info`; a removed report no longer blocks a new one for the same terminal and commodity.
- Output: `id`, `type`, `date_removed`. Codes: `missing_id`, `report_not_found`, `report_consolidated`, `type_not_available` and the auth codes.

## Observed by third parties (2026-10-09)

Tag **[3P-OBS]**. These are observations of other clients' traffic; our own `is_production=0` write check still has to confirm them before an adapter relies on them.

## Terms of use

[TERMS] §1.4 allows personal, non-commercial use. §5 (API terms): endpoints may change or be removed, users must follow the documentation, access can be terminated for misuse. §3.7: whoever uploads an image confirms the right to share it and grants UEX a licence; public content may be reused by third parties. §3.8: accounts only from age 18. §6 (Datarunner agreement): reports must be accurate and "reported from the location specified"; unusual reports may be declined; repeated improper reports can lead to locks or bans. The terms say nothing about third-party clients, a User-Agent convention or republishing API responses (point 7). Corrected 2026-10-09: the terms live at `/about/terms`, not `/about/legal`.

**UEX's permission (2026-10-25)** [UEX]:

- An open-source client is welcome; other third-party clients already submit through `data_submit`. UEX asks for: only values the player actually saw at that terminal, confirmed by the player; **one terminal per request**; the player's own secret key. There is no client registration beyond the app token. A User-Agent with the client's name and version is appreciated, and `X-Client-Version` is fine to send.
- **Fixtures:** small anonymised fixtures (a handful of terminals, commodities and prices) may be committed to the public repository; full dumps of the price tables may not, and are fetched at run time (point 7, O-50).
- **Naming:** UEX has no formal brand guidelines. Naming UEX is fine ("a Datarunner client for UEX"), as long as it is clear that Tallyline is an independent community project, not made or endorsed by UEX (O-106).
- **Test accounts:** none are issued. UEX suggests the developer's own key with `is_production=0`; read calls need no account (O-69).
- **Channel:** e-mail is the right channel for questions like these.
