# Requirements

> **Doc type:** Living spec — binding. Last reviewed: 2026-10-08.

Priorities: **M** = Must (1.0), **S** = Should (1.x), **C** = Could (later).

IDs are stable and never reused or renumbered. A dropped requirement keeps its row with the priority `Withdrawn (YYYY-MM-DD)`, the reason and its replacement; a new requirement takes the next free number in its area ([CLAUDE.md](../../CLAUDE.md), "Requirements, decisions and open points"). Open owner decisions and verifications are tracked in [docs/adr/0000-open-points.md](../adr/0000-open-points.md); the assumptions stay in this document.

## Goal

Players (UEX DataRunners) use the client to capture commodity terminal data from Star Citizen and provide it to UEX. There are two ways to do this:

- **manually:** fast, keyboard-driven input, with current UEX values shown as reference (not prefilled, R-MAN-2)
- **via screenshot:** OCR, validation, review, submission

Current UEX data (terminals, commodities, latest prices, status levels, game version, tolerances) serve as **default values and constraints** for recognition and selection.

## Terms

The complete, binding domain language (Ubiquitous Language) is in [11-ddd-and-tdd.md](11-ddd-and-tdd.md) §A1. Only the short version here:

| Term | Meaning |
|---|---|
| **Capture** | A screenshot |
| **Scan** | A capture after OCR analysis |
| **Report** | The aggregation of all scans of one terminal, one side (buy = "Buy", sell = "Local Market Value") and one environment within a time window (grouping rule R-OCR-13). The report is the unit sent to `POST /data_submit`. |
| **Send threshold** | Minimum confidence at or above which a field may be sent without confirmation (initial value 0.80, see [07](07-ocr-concept.md) §2.6). Mandatory fields ([11](11-ddd-and-tdd.md) §A1) below it must be confirmed or corrected; an optional field below it is not sent. |
| **Prior** | The latest UEX value (price, SCU, status) for the combination of terminal, commodity and side, with its age; without one, the commodity-wide average price is a coarse substitute (R-VAL-2a) |

| R-CAP-1a | **Manual import (default):** A click on **"Import"** (globally for all active folders or per folder) imports all files newer than the folder's cutoff (R-CAP-1) that have not been processed yet. | R-CAP-1b | **Automatic import (opt-in per folder):** When enabled, newly created files are taken over immediately. Technique: `WatchService` (`ENTRY_CREATE`/`ENTRY_MODIFY`) plus polling fallback (default 2 s) if the WatchService cannot be registered or the folder is on a file system whose change events are unreliable (FUSE and network mounts such as SMB/NFS); polling can also be forced per folder. On startup and after enabling, a catch-up scan runs for files created while the app was closed or the mode was off (can be disabled); it respects the folder's cutoff (R-CAP-1). | M |
| R-CAP-1c | **Read only when fully written:** A file counts as complete when its size and `lastModified` are stable for a quiet period (default 750 ms) and it can be decoded as an image. Partial files are retried (with backoff, at most 30 s) and then shown as an error with a reason. Files whose content is an unsupported format (R-CAP-8) are not retried: once their size is stable they are set aside at once with the R-CAP-8 message. Before decoding, the header is checked against hard limits (file size, declared pixel count, embedded ICC profile size; settings with documented start values far above the R-OCR-17 pixel budget). A file above a limit is set aside with a reason and never decoded ([02](02-architecture.md) §9). | M |
| R-CAP-1d | **Processed-file register** (SQLite): path, size, `lastModified` and content hash of every imported file. This way neither "Import" nor the watcher reads the same file twice, even after renaming or copying (hash). Register entries are kept independently of capture and working-copy retention (R-CAP-7), so a purged capture is not re-imported while its file is still in a watched folder; an entry is pruned only after 1 year (setting) and only once its file no longer exists at the recorded path. Per file there is a "Re-import" action: it re-runs recognition on the existing Capture (`rescan()`, [11](11-ddd-and-tdd.md) §A3) and never creates a second Capture for the same content; for a file set aside at intake, before a Capture existed, it decodes the file again. It is offered only while no active report references the Capture (it failed, was set aside, or its report was discarded); otherwise it is disabled with the reason, and a submitted report is corrected via R-SUB-10 instead. A file is registered in state `decoding` before its first decode. If the app ends during that decode (e.g. a decoder crash), the file is set aside as failed at the next start and decoded again only via "Re-import", so a poison file cannot cause a crash loop. | M |
| R-CAP-1e | Status visible per folder: enabled/disabled, mode (manual/automatic), watched yes/no (and why not, e.g. folder missing or no permissions), polling active, last file, number of pending files. If a folder is missing, it is flagged and not silently removed. | M |
| R-CAP-2 | Further input paths: drag & drop, Ctrl+V, file dialog (multiple selection), optional clipboard monitoring (opt-in, default off; it detects a clipboard change before reading any image, [02](02-architecture.md) §4a; on Linux per A23) with fingerprint deduplication | M |
| R-CAP-3 | The environment is derived from the folder path (or set fixed per folder), the game version from UEX (`game_versions`). If the environment is unknown, the capture waits as "environment pending" until the user sets it (R-CAP-1); there is no hard-coded fallback. From R-CAP-10 on (M4), the folder's environment is cross-checked with the running game's channel. | M |
| R-CAP-3a | **Environment mapping to UEX:** UEX only knows `live` and `ptu`. Default mapping: LIVE and HOTFIX → `live`, PTU/EPTU/TECH-PREVIEW → `ptu`. Configurable; the mapping must be verified against UEX (assumption A9). If no reports are accepted for the target (`is_accepting_*` = 0 or `commodity.is_accepted` = 0), release still works and the jobs are held until acceptance reopens (R-SUB-5, R-SUB-11). | M |
| R-CAP-3b | **Game version at capture time:** the app keeps a persisted history of observed versions **per UEX environment** (`live`/`ptu`): version, first seen, last seen – only from successful `game_versions` fetches, never from the cached state. Besides the TTL refresh ([06](06-uex-api.md)), `game_versions` is fetched at startup, before an import batch is versioned if the last successful fetch is older than `versionStampMaxAge` (setting, start value 30 min), when the game starts (R-VLM-2) and at most 15 min before every send attempt (R-SUB-5). Until the first successful fetch after installation (e.g. an offline first start, R-UI-13), new captures wait in state `Imported` and are neither versioned nor scanned; that fetch moves them to `Ready` or "environment pending" (default until the owner decides). Each capture gets the version for its capture time t (R-CAP-5) and environment, derived once the environment is known ("environment pending", R-CAP-1):<br/>• **certain:** t lies between first and last seen of one version;<br/>• **provisional:** t is after the last successful fetch; the newest version is used, and the next successful fetch makes it certain (same version) or uncertain (new version);<br/>• **uncertain:** t lies between the last seen of one version and the first seen of the next (e.g. a catch-up import after a patch), or before the oldest observation (including an empty history after the first install, where the version is assigned at the first successful fetch); an uncertain capture time (R-CAP-5) makes the version uncertain as well, and so do different versions among the captures of one report (a patch inside the grouping window);<br/>• **unknown:** UEX reports no version for the environment (e.g. `ptu` is `null`); release is blocked until a version is observed or the report is discarded.<br/>A report with an uncertain version, or whose version is no longer the newest observed one (patch between capture and sending), is marked "to be checked" (I5), and release requires the user's choice. A queued job that meets a version change at a send attempt returns to Draft marked the same way (R-SUB-5) and shows in the queue, never through a dialog (R-UI-16). The choice is made on the report (I5): the user keeps the capture-time version, switches an uncertain version to another version from that environment's history observed around the capture time, or discards the report (state `Discarded`, reason version changed). Once the user confirms or enters an uncertain capture time (R-VAL-6), the version valid at that time is used. The report is sent with the chosen version and never silently relabelled with the current one; whether UEX accepts an older version is unverified (A18). Known gap: if UEX publishes a new version late, or a patch keeps the version string, captures get the old version (A17). | M |
| R-CAP-4 | Automatic detection of the SC installation: RSI Launcher log `Launching Star Citizen … from (…)`, running process `Bin64/StarCitizen.exe`, default paths. On Linux additionally Wine/Proton prefixes (see assumption A3). | S |
| R-CAP-5 | **Capture time with its source** (`CaptureTime`):<br/>• **FILE_NAME:** a listed, tested file-name pattern per known tool (SC screenshot key and the tools recommended in R-DOC-1; patterns verified with real files, A19), read as local time in the system time zone and converted with the zone rules. If it is ambiguous (autumn DST overlap), the offset whose instant is closest to `lastModified` is used; if neither candidate lies within a tolerance (capture settings record, start value 2 min), the earlier instant is used. If the local time does not exist (spring DST gap), or it is later than `lastModified` by more than the tolerance (zone or clock mismatch), `lastModified` is used. These three cases (overlap, gap, mismatch) make the time uncertain (see below). A file-name time earlier than `lastModified` is normal for copies and is not flagged. Tests use a fixed `Clock` and zone (Europe/Berlin around 2026-10-25 and 2026-03-29);<br/>• **FILE_MTIME:** `lastModified`;<br/>• **CLIPBOARD_EVENT:** the time at which clipboard monitoring detected the change (the image appeared while the app was running);<br/>• **PASTE_TIME:** the time of Ctrl+V or of dropping image data without a file (no information about the capture);<br/>• **USER:** entered or confirmed by the user (R-VAL-6).<br/>The time counts as **certain** for FILE_NAME (except in the three overlap, gap and mismatch cases), CLIPBOARD_EVENT and USER, and for FILE_MTIME of a file the watcher saw appear while the app was running (mtime within a tolerance of the first sighting; setting). Otherwise – those three FILE_NAME cases, FILE_MTIME from the catch-up scan, "Import", drag & drop or the file dialog, and PASTE_TIME – the capture gets the finding `CaptureTimeUncertain` (R-VAL-6), because copied, downloaded or synced files can carry the time of the copy and pasted image data carries none. The source is shown in the queue and the report editor. Grouping (R-OCR-13), sessions (R-UI-14) and the "only files newer than" filter (R-CAP-1) use the same capture time. The app detects duplicates via content hash. | M |
| R-CAP-6 | Optional cleanup function: delete or archive originals after successful submission. Default is **off**. | S |
| R-CAP-7 | **Working copies:** Per capture, the app stores the perspective-corrected panel crops (not the full-screen screenshot) in its data directory, at about 1:1 source scale so that re-reads keep the source legibility. The crops are stored **redacted**: their extent and the header-band fill follow R-SUB-7 and are applied before anything is persisted. Review, AI re-check, upload and the exports (R-QA-5, R-NF-6) use only these crops, never the original. Upload, AI re-check and review therefore also work if the original was moved or deleted. **Retention** (periods are settings, counted from the last state change):<br/>• **never purged automatically:** working copies of reports in Draft, Released, Queued, WaitingForCooldown or OutcomeUnknown (including jobs held or paused, R-SUB-11), and of captures not yet scanned (e.g. environment pending);<br/>• **7 days:** working copies of reports in Submitted, PartiallyAccepted, Rejected or Withdrawn, of discarded reports (state `Discarded`, counted from the discard) and of failed captures;<br/>• **1 year:** history metadata;<br/>• **evidence-dependent actions:** "duplicate as new draft" (R-SUB-10, R-SUB-11) and the R-QA-5 export are offered only while the working copies exist; the duplicate keeps the original `observedAt`, so R-VAL-6 still applies. Drafts older than the R-VAL-6 hard limit are offered for discard, never discarded automatically;<br/>• **disk space:** before writing working copies, the app checks the free space of the data directory against a threshold (setting; start value set in M3 from measured working-copy sizes). Below it, import pauses with a visible needs-action state on the folder status and in the queue; working copies of open reports are never deleted to make room. Diagnostics shows the size per retention category. | M |
| R-CAP-8 | **Image formats and colour encoding:** the format is detected from the file content (magic bytes), not from the extension.<br/>• **Read:** PNG (8 and 16 bit per channel), JPEG (reportedly the format of the SC screenshot key, A16) and BMP, converted to an 8-bit sRGB `ImageRaster`; 16-bit samples are scaled from the raster, not via `getRGB`.<br/>• **Colour metadata is evaluated explicitly** in `adapter-files` (an `ImageReader` with metadata enabled, or a small PNG chunk walker before `IDAT`), because `ImageIO.read` skips these chunks, the JDK never applies PNG `iCCP`/`gAMA`/`cHRM` to the pixels, and it does not know `cICP`. PNG precedence: `cICP` > `iCCP` > `sRGB` > `gAMA`/`cHRM` (PNG 3rd edition). `iCCP` is applied via `ICC_Profile` and `ColorConvertOp`; a JPEG APP2 ICC profile is applied by the JDK reader (pinned by a decode fixture, [07](07-ocr-concept.md) §4); `gAMA` is applied; `cHRM` primaries other than BT.709 (without `iCCP`/`cICP`) count as an encoding the adapter cannot convert.<br/>• **Never read as sRGB:** a `cICP` with PQ (16) or HLG (18) transfer (e.g. `09 10 00 01`), any other `cICP` except BT.709 primaries (1) with sRGB transfer (13), and any other encoding the adapter cannot convert. In 1.0 such a file is set aside with the reason "HDR or unsupported colour encoding – use an SDR copy". A tone-mapping path (PQ EOTF, BT.2020 → BT.709, reference white 203 cd/m² by default, highlight roll-off, sRGB OETF; parameters in a settings record) is a 1.x option and needs an ADR on where it lives (adapter or a core HDR raster type).<br/>• **HDR containers** (JPEG XR, AVIF, OpenEXR, HEIF) are not decoded. Folder import always lists files with the extensions `.jxr`, `.avif` and `.exr` in addition to the folder's extension filter; drag & drop, Ctrl+V and the file dialog recognise these formats by content. Once their size is stable they are set aside at once, without decode retries (R-CAP-1c). If a supported copy of the same capture is part of the same import (Game Bar writes a PNG next to the `.jxr`; pairing rule verified in M2, A16), the HDR file counts as "HDR original – SDR copy used" and needs no action. If the copy exists but was not imported, the message offers "Import the SDR copy". Otherwise the import result shows "n new, m skipped, k in HDR format" with the message "HDR screenshot format (JPEG XR/AVIF/EXR) – not supported", a hint that is tool-specific where the folder or file name identifies the tool (Game Bar: use the PNG next to it; NVIDIA overlay: reportedly JXR or a PQ-encoded PNG, use Game Bar or turn HDR off while capturing; gamescope: use the SC screenshot key or Spectacle; OBS on Windows: writes no SDR copy, use the SC screenshot key) or otherwise lists the alternatives, and a link to the capture tips (R-DOC-1). Messages offer only actions that exist.<br/>• Golden tests use synthetic decode fixtures (07 §4). | M |
| R-CAP-9 | **Capture check:** Diagnostics, and the onboarding as a skippable step after the folder selection (once OCR exists), offer "Check a screenshot". The user picks one screenshot of any commodity terminal. It is analysed with the normal pipeline but is **not** added to the queue or the processed-file register, and nothing is sent. The result lists, each with icon and text: file format and colour encoding (R-CAP-8), image size, panel located yes/no, measured price-digit cap height against the limits (R-OCR-17), tone state (R-OCR-18), and one concrete piece of advice per problem, worded per OS (from R-DOC-1). The same findings are shown per capture in the report editor via R-VAL-1/R-UI-4; there is no separate logic. | S |
| R-CAP-10 | **Environment cross-check with the running game:** the process monitor (R-VLM-2) also records the channel folder of the running game from the executable path (`…\StarCitizen\<CHANNEL>\Bin64\StarCitizen.exe`; on Linux from argv[0], A7) with timestamps, persisted next to the version history (R-CAP-3b); a channel it cannot determine is "unknown". On import, if a known channel was observed at the capture time and maps (R-CAP-3a) to another UEX environment than the folder's environment, the capture waits as "environment pending" (R-CAP-1) with the observed channel offered as a suggestion, not preselected. For a manual report, a running channel that maps to another UEX environment than the selected one is highlighted, and release needs an explicit confirmation of the environment. The confirmation is stored on the report with the observed running channel and the time; at release, the running channel's environment is compared with the report's, and release is refused with `EnvironmentUnconfirmed` while they differ and the report holds no confirmation for that running channel; a different running channel at a later release needs a new confirmation, and changing the report's environment revokes it (default until the owner decides). No observation, or an unknown channel, never counts as a mismatch. Until this exists, the environment is not cross-checked. | S |

## Manual capture (MAN)

| ID | Requirement | Prio |
|---|---|---|
| R-MAN-1 | Terminal selection via search field (fuzzy over name, nickname, location, system), filter by star system, "recently used" | M |
| R-MAN-2 | After choosing the terminal, the list of the terminal's known commodities appears (from `commodities_prices`). The current UEX values are shown **as a reference next to the input field** (including the age of the value), **not as a prefilled value**. Only rows that were actively entered or explicitly taken over by keystroke are sent. Their values have origin `USER` ([11](11-ddd-and-tdd.md) §A1). This way no outdated values end up unchecked at UEX as a "fresh" report. An "Add commodity" action picks from the global vocabulary (`GET /commodities`, filtered by `is_buyable`/`is_sellable` for the side being entered and by availability in the report's environment). Such a row gets the R-UI-10 level "no reference value", counts as an unexpected commodity in the R-UI-12 summary and is never added automatically. | M |
| R-MAN-3 | Full keyboard operation: Tab/Enter, number shortcuts for status levels 1–7 | M |
| R-MAN-4 | Manual reports go through the same validation (VAL) as OCR reports | M |
| R-MAN-5 | Manual reports can attach a screenshot. If the client knows that a screenshot is mandatory for the user (evaluation phase of new DataRunners, `screenshot_required`), this is shown in advance and submission without an image is blocked. Sources, in order: a verified field from `/user` ([06](06-uex-api.md) open point 10); otherwise the most recent `screenshot_required` answer for this account (stored with its date, from a real or test submission). Without such a source, a manual report without an image may be released; a `screenshot_required` answer returns it to Draft with a finding (R-SUB-11), and the requirement is remembered from then on. The stored flag is shown with its date, and the user can clear it ("try without screenshot"). (Assumption A11.) | M |
| R-MAN-6 | Manual reports have an environment and use the current UEX game version of that environment. There is no fixed default: the environment of the user's last manual report is preselected and shown prominently in the entry view and in the release summary; on first use the user chooses it. Once R-CAP-10 exists (M4), a running game on another channel is flagged. | M |

## Recognition (OCR)

| ID | Requirement | Prio |
|---|---|---|
| R-OCR-1 | Local OCR (no cloud) with PaddleOCR models (detection + recognition) via ONNX Runtime; models bundled, license and hash evidence in `NOTICE` | M |
| R-OCR-2 | Localization of the terminal panel via text anchors and luma-gradient frame edges (no theme colour, R-OCR-18), perspective correction. If it fails, the user can set the corners or the crop manually; the app never aborts hard. | M |
| R-OCR-3 | Theme-agnostic: orange/red (e.g. Patch City/Pyro), blue and other terminal themes. Layout profiles are data-driven. | M |
| R-OCR-4 | Recognition of side (Buy / Local Market Value, active tab) and of the section per card (IN STOCK / OUT OF STOCK / IN DEMAND / NO DEMAND / SELLABLE CARGO), from headers inside the shop panel only ([07](07-ocr-concept.md) §2.3, §2.5b). The content of SELLABLE CARGO and of a shop-panel NO DEMAND section is unverified (A21). | M |
| R-OCR-5 | Robust number parser: strip currency symbol `¤` (glyph box aligned with the recognized characters, [07](07-ocr-concept.md) §2.4), determine thousands and decimal separators structurally, optional K/M suffix, suffix `/SCU` | M |
| R-OCR-6 | Repair of confusable digits ({0,6,8,9}, possibly others from the corpus): repair candidates only at uncertain confusable positions (definition in [07](07-ocr-concept.md) §2.5), only with an unambiguous candidate, and automatically only with an independent witness (R-VAL-2b) | M |
| R-OCR-7 | Commodity names are resolved against the full UEX vocabulary of the environment and the localized `global.ini` names, before and independently of any terminal assortment ([07](07-ocr-concept.md) §2.5). Robust against line breaks and overlap with the SCU value. | M |
| R-OCR-8 | Terminal and location recognition primarily from the location field under "YOUR INVENTORIES". Every candidate, including a single one, is checked against its assortment for the captured side by containment ([07](07-ocr-concept.md) §2.5 item 2) | M |
| R-OCR-9 | "AVAILABLE CARGO SIZE (SCU)" → `container_sizes` | S |
| R-OCR-10 | Status-bar witness for the status: color and fill level of the vertical stock bar or the color of the status text, matched against the OCR status text (a witness, not a `Reader`; [11](11-ddd-and-tdd.md) §A1) | S |
| R-OCR-11 | Stitching of multiple scrolled screenshots of one terminal or side – **even without overlap** (order via the scrollbar, merging via the commodity ID). Cut-off cards at the edge are only taken over if the card is fully visible (top and bottom card edge inside the viewport, [07](07-ocr-concept.md) §2.3). Possible gaps (scrollbar, UEX assortment) are shown. Conflicting values for the same field from two captures follow one rule (07 §2.5b). If the captures are less than 60 s apart, or either reading is below the send threshold, the field is `Ambiguous` (select; the reading farther from the viewport edge is only the suggestion). Otherwise the later reading is proposed with the finding `Superseded` (e.g. after the player's own trade) and needs a confirmation. If either capture's time carries `CaptureTimeUncertain` (R-CAP-5), "later capture" is never decided automatically: the field is `Ambiguous` and the conflict is shown to the user. A new capture or a merge never silently changes a field the user confirmed or corrected ([11](11-ddd-and-tdd.md) §A3, I7). | M |
| R-OCR-12 | Processing in the background (bounded parallelism, R-NF-3), the UI never blocks. **Runtime target:** p95 per resolution class on the reference machine ([04](04-roadmap.md) M2) with the default OCR pool and `OcrRuntimeSettings`; start goal < 3 s per screenshot. The target is set from the M2 baseline before release 0.5 and re-measured in M4. If the target conflicts with the resource limits of R-NF-3, the limits win and the target is revised. | M |
| R-OCR-13 | **Report grouping:** Scans belong to one report if terminal, side and environment are the same and the time gap to the previous scan of the group is ≤ 10 min (configurable). The user can split and merge reports in the UI. A scan with an unclear terminal or side forms its own group until both are resolved. A scan whose capture time carries `CaptureTimeUncertain` (R-CAP-5) also forms its own group until the user confirms the time or merges it. Captures never join a report that is no longer in state Draft; they start a new report. | M |
| R-OCR-14 | **Neighbor names** (distinguished only by a short token such as "SIZE 1"/"SIZE 7") are only assigned automatically if the distinguishing token was read exactly, otherwise `Ambiguous` (07 §2.5). | M |
| R-OCR-15 | Dimmed cards (hypothesis A14: not buyable) are read with their own contrast normalization and not discarded as a partial card. | S |
| R-OCR-16 | **Not a terminal screenshot:** images that do not show a commodity terminal (other UI, other app) are recognized as such and set aside with a notice and a "process anyway / crop manually" action – never a generic "failed to process" error (fix for F7). The notice names "terminal too far away or too small in the image" as a possible cause next to "other screen". A valid shop panel whose "YOUR INVENTORIES" field shows another location (ship, other station's storage) is **not** rejected: the terminal counts as unknown and the selection is mandatory. If that location is itself a valid UEX location, the assortment check detects it ([07](07-ocr-concept.md) §2.5 item 2, finding `LocationAssortmentMismatch`); the session context is only a hint. From M3 on, a capture with terminal structure (price or cargo-box rows) but no English layout anchor gets the hint "layout labels not recognised – game language not English? (only English is supported before 1.0)" instead of "not a terminal" (07 §2.1 item 3); full `global.ini` support follows with R-L10N-2. Images without a source file are first written to the app's inbox like a file ([02](02-architecture.md) §4a). If an image pasted with Ctrl+V or dropped as image data is set aside here, its inbox copy is kept only until the user decides, at most for the "failed captures" retention of R-CAP-7. With clipboard monitoring on, an image that is set aside as not a terminal is never kept: its inbox copy is deleted at once, no working copy is stored, it is not listed with "process anyway / crop manually", and only a count is shown. | M |
| R-OCR-17 | **Resolution and scale independence:** the measured text size decides whether a capture is readable, never its pixel dimensions.<br/>• **Covered inputs:** 1920×1080 up to 3840×2160, 21:9 and 32:9 (including native 7680×2160), multi-monitor desktops (e.g. 5760×1080), windowed captures (also below 1080p) and DSR/VSR captures above the monitor resolution. The image size is never assumed to equal a display or render resolution.<br/>• **Geometry:** the panel is located via text anchors and normalized by homography; all layout tolerances are relative to the normalized panel, never absolute pixels ([07](07-ocr-concept.md) §2.1 items 1, 4 and 6).<br/>• **Pixel budget:** an input above the budget (setting, start value 20 MP, so that native 7680×2160 is not reduced) is reduced by an integer box factor while decoding in `adapter-files` (info finding `Downscaled` with the original size), so that the memory budget (R-NF-3) holds. Inputs up to 7680×4320 never cause an out-of-memory error (resource test through decode, locate and ONNX Runtime with the shipped launcher options). The text-size gate runs on the raster that is actually read.<br/>• **Text-size gate:** the reference is the **cap height of the price digits** in source pixels. Before layout it is estimated from the anchors via per-theme ratios in the layout profile (Stanton blue, measured on the unverified entry `pyro-gateway-stanton-01`: price ≈ 0.84 × "SHOP INVENTORY" ≈ 1.13 × "AVAILABLE CARGO SIZE"). After layout it is measured on the price digits, and the **smallest value over the complete cards** (07 §2.3) counts (perspective changed it by 5–10 % between cards in the sample). The location field is gated the same way. Start values: **≥ 8 px** normal; **6 to < 8 px** (*confirm limit*) finding `SmallText`, numeric fields at most "confirm"; **< 6 px** (*lower limit*) finding `TextTooSmall`, numeric fields appear only as suggestions at level "correct" and are never part of "Accept all confident"; names are still resolved.<br/>• **Origin of the start values:** a preliminary box-downscale experiment during planning (one theme, third-party export of PP-OCRv6 small; nearest-neighbour downscaling was 1–2 px worse), so they may be optimistic for in-engine rendering. M2 calibrates them per theme with the official export ([04](04-roadmap.md) M2, 07 §4).<br/>• **Wording:** the finding text gives the measured value and the target and is advice for the **next** capture, never a demand to redo this one, e.g. "Text is small in this capture (price digits ≈ 7 px, reliable from 8 px). Values need confirmation. Next time move closer so the terminal screen fills about three quarters of the image height, or use a higher game resolution." The crop is always shown so the user can type the values.<br/>• The two limits are the only legibility thresholds on source-image content (legibility is absolute, so they are in source pixels). They are release-calibrated (R-NF-5); they and the pixel budget, which bounds memory (R-NF-3), live in a typed settings record with documented defaults and are not user-editable. | M |
| R-OCR-18 | **HDR and tone variations:** recognition works with captures taken with HDR on or off. Files whose colour encoding is known to be HDR are handled by R-CAP-8, not here.<br/>• After locate, each located panel is **analysed and normalized per panel** ([07](07-ocr-concept.md) §2.1 item 7): black and white points from percentiles, saturated-stroke share and saturation relative to the layout profile's SDR reference. The normalized panel drives colour and geometry decisions; whether the recognizer gets the normalized or the original crop is decided by the M2 eval. Colour decisions (tab, status colour, hover) are relative comparisons within the panel and use hue/relative saturation, never absolute RGB thresholds.<br/>• **Two tone problems are detected separately:** **washed out** (raised black level and compressed range, typical for 8-bit captures of an HDR desktop and for untagged PQ-encoded files; recoverable by the stretch) gives the finding `LowContrastCapture`; **clipped** (glyph detail lost to saturation; calibrated so that ordinary SDR captures with white glyph cores do not trigger it) gives `ClippedHighlights`. Start rule: under either finding every numeric field gets at most "confirm"; M3 decides per finding whether the cap stays (07 §2.1 item 7). The tone thresholds behind both findings (black and white point, saturated-stroke share, saturation) are release-calibrated on paired captures (07 §4) and not user-editable (R-NF-5).<br/>• The finding text names likely causes without claiming to know them, e.g. "possibly a screenshot of an HDR display, or very high in-game brightness/gamma", and links to the capture tips for the user's OS (R-DOC-1).<br/>• **Hints are non-modal.** The report editor shows them per capture. The queue shows one notice per input source (folder, drag & drop, clipboard) and session once N consecutive captures from that source carry the same finding (setting, start value 3), e.g. "Recent captures from <folder> look washed out – see capture tips". "Don't show again for this source" hides the notice, never the per-capture finding. | M |
| R-OCR-19 | **Layout validated per game version:** every layout profile lists the game versions it was validated on. A version counts as validated for a profile only if verified corpus captures of the profile's theme on that version (`verified: true`, `conditions.gameVersion` set; Buy and Sell) show no silently wrong field and a field accuracy not below the profile's frozen baseline, evaluated without this cap ([07](07-ocr-concept.md) §4); entries with `gameVersion: null` or `verified: false` never validate a version. If a report's game version is newer than all validated versions of its profile, every recognized field is capped below the send threshold (finding `UnvalidatedGameVersion`) until a release validates the version. The cap applies to the fused value, i.e. to OCR and VLM readings alike (07 §2.7). PTU versions are no exception: a PTU version newer than all validated versions stays capped until verified PTU captures validate it. The cap is re-evaluated whenever a report's game version is set or changed (R-CAP-3b). The user can lift it for the current session after a warning. This protects UEX when a patch changes the terminal UI in a way that still reads "cleanly" – from the moment the app has observed the new version (A17). | M |

## Optional AI recognition (VLM)

The classic OCR (above) is the **default path** and always runs, even while playing. In addition, a **local vision language model (VLM)** can be enabled via [Ollama](https://ollama.com). It needs a lot of VRAM or CPU and therefore by default runs **only when Star Citizen is closed**. This way you can work in the game without AI and have the AI re-check afterwards.

| R-NF-12 | **No telemetry, including ONNX Runtime's** (privacy gate, [ADR-0003](../adr/0003-licence-and-contributions.md)): the app sends no telemetry, analytics, crash reports or remote logs, and no dependency does so on its behalf; every network destination and local store is in the data-flow inventory ([02](02-architecture.md) §9). Until the mitigation is verified, 02 §9 lists ORT telemetry as a known exception, and no release bundles ONNX Runtime. Test: from M2 on, the packaged-app smoke test on Linux records the network connections that the app process attempts while it creates an ORT session and fails on any. | M |
