# Requirements

Priorities: **M** = Must (1.0), **S** = Should (1.x), **C** = Could (later).

## Goal

Players (UEX DataRunners) use the client to capture commodity terminal data from Star Citizen and provide it to UEX. There are two ways to do this:

- **manually:** fast, keyboard-driven input, with current UEX values shown as reference (not prefilled, R-MAN-2)
- **via screenshot:** OCR, validation, review, submission

Current UEX data (terminals, commodities, latest prices, status levels, game version, tolerances) serve as **default values and constraints** for recognition and selection.

## Terms

The complete, binding domain language (Ubiquitous Language) is in [11-ddd-and-tdd.md](11-ddd-and-tdd.md) §A1. Only the short version here:

| Term | Meaning |
|---|---|
| **Capture** | A screenshot |
| **Scan** | A capture after OCR analysis |
| **Report** | The aggregation of all scans of one terminal, one side (buy = "Buy", sell = "Local Market Value") and one environment within a time window (grouping rule R-OCR-13). The report is the unit sent to `POST /data_submit`. |
| **Send threshold** | Minimum confidence at or above which a field may be sent without confirmation (initial value 0.80, see [07](07-ocr-concept.md) §2.6). Fields below it must be confirmed or corrected. |
| **Prior** | The UEX reference value (latest or average price, SCU, status) for the combination of terminal, commodity and side |

## Capture (CAP)

| ID | Requirement | Prio |
|---|---|---|
| R-CAP-1 | **User-defined image folders:** add, remove and enable/disable any number of folders. Configurable per folder: environment (**automatic from the path** – default – or fixed LIVE/PTU/EPTU/HOTFIX/TECH-PREVIEW or **ask for every image** – images then wait as "environment pending" in the queue; the app never opens a dialog by itself while the game may be running), include subfolders (yes/no), file types (default `png`, `jpg`, `jpeg`, `bmp`; the known HDR container types are always listed and reported, R-CAP-8), optionally "only files newer than …". The SC screenshot folders are only **suggested** during onboarding; the user confirms them. | M |
| R-CAP-1a | **Manual import (default):** A click on **"Import"** (globally for all active folders or per folder) imports all files that have not been processed yet. Result: "n new images taken over, m skipped". Optionally there is a preview list for deselecting individual files. | M |
| R-CAP-1b | **Automatic import (opt-in per folder):** When enabled, newly created files are taken over immediately. Technique: `WatchService` (`ENTRY_CREATE`/`ENTRY_MODIFY`) plus polling fallback (default 2 s) if the WatchService is unreliable (Wine prefixes, network drives) or cannot be registered. On startup and after enabling, a catch-up scan runs for files created while the app was closed or the mode was off (can be disabled). | M |
| R-CAP-1c | **Read only when fully written:** A file counts as complete when its size and `lastModified` are stable for a quiet period (default 750 ms) and it can be decoded as an image. Partial files are retried (with backoff, at most 30 s) and then shown as an error with a reason. Files whose content is an unsupported format (R-CAP-8) are not retried: once their size is stable they are set aside at once with the R-CAP-8 message. | M |
| R-CAP-1d | **Processed-file register** (SQLite): path, size, `lastModified` and content hash of every imported file. This way neither "Import" nor the watcher reads the same file twice, even after renaming or copying (hash). Per file there is a "Re-import" action. | M |
| R-CAP-1e | Status visible per folder: mode (manual/automatic), watched yes/no (and why not, e.g. folder missing or no permissions), polling active, last file, number of pending files. If a folder is missing, it is flagged and not silently removed. | M |
| R-CAP-2 | Further input paths: drag & drop, Ctrl+V, file dialog (multiple selection), optional clipboard monitoring with fingerprint deduplication | M |
| R-CAP-3 | The environment is derived from the folder path (or set fixed per folder), the game version from UEX (`game_versions`). If the environment is unknown, the app asks; there is no hard-coded fallback. | M |
| R-CAP-3a | **Environment mapping to UEX:** UEX only knows `live` and `ptu`. Default mapping: LIVE and HOTFIX → `live`, PTU/EPTU/TECH-PREVIEW → `ptu`. Configurable; the mapping must be verified against UEX (assumption A9). If no reports are accepted for the target (`is_accepting_*`), submission is blocked. | M |
| R-CAP-3b | **Game version at capture time:** On import, the version valid at capture time is recorded (cached state of `game_versions`). If the version changed between capture and submission (patch day), the app warns and requires a confirmation or discards the report. The app keeps a local history of observed version changes (timestamp of first observation). If a capture is older than the last observed change and the app was not running in between (e.g. catch-up import after a patch), the version is marked **uncertain** and the user must confirm it. | M |
| R-CAP-4 | Automatic detection of the SC installation: RSI Launcher log `Launching Star Citizen … from (…)`, running process `Bin64/StarCitizen.exe`, default paths. On Linux additionally Wine/Proton prefixes (see assumption A3). | S |
| R-CAP-5 | Capture time from the file name (regex, interpreted in the system time zone), fallback to `lastModified`. The app detects duplicates via content hash. | M |
| R-CAP-6 | Optional cleanup function: delete or archive originals after successful submission. Default is **off**. | S |
| R-CAP-7 | **Working copies:** Per capture, the app stores the perspective-corrected panel crops (not the full-screen screenshot) in its data directory, at about 1:1 source scale so that re-reads keep the source legibility. Upload, AI re-check and review therefore also work if the original was moved or deleted. Retention (configurable per category): working copies 7 days after successful submission; discarded drafts and failed captures 7 days; history 1 year. Diagnostics shows the size of the data directory. | M |
| R-CAP-8 | **Image formats and colour encoding:** the format is detected from the file content (magic bytes), not from the extension.<br/>• **Read:** PNG (8 and 16 bit per channel), JPEG (reportedly the format of the SC screenshot key, A16) and BMP, converted to an 8-bit sRGB `ImageRaster`; 16-bit samples are scaled from the raster, not via `getRGB`.<br/>• **Colour metadata is evaluated explicitly** in `adapter-files` (an `ImageReader` with metadata enabled, or a small PNG chunk walker before `IDAT`), because `ImageIO.read` skips these chunks, the JDK never applies PNG `iCCP`/`gAMA`/`cHRM` to the pixels, and it does not know `cICP`. PNG precedence: `cICP` > `iCCP` > `sRGB` > `gAMA`/`cHRM` (PNG 3rd edition). `iCCP` is applied via `ICC_Profile` and `ColorConvertOp`; a JPEG APP2 ICC profile is applied by the JDK reader (pinned by a decode fixture, [07](07-ocr-concept.md) §4); `gAMA` is applied; `cHRM` primaries other than BT.709 (without `iCCP`/`cICP`) count as an encoding the adapter cannot convert.<br/>• **Never read as sRGB:** a `cICP` with PQ (16) or HLG (18) transfer (e.g. `09 10 00 01`), any other `cICP` except BT.709 primaries (1) with sRGB transfer (13), and any other encoding the adapter cannot convert. In 1.0 such a file is set aside with the reason "HDR or unsupported colour encoding – use an SDR copy". A tone-mapping path (PQ EOTF, BT.2020 → BT.709, reference white 203 cd/m² by default, highlight roll-off, sRGB OETF; parameters in a settings record) is a 1.x option and needs an ADR on where it lives (adapter or a core HDR raster type).<br/>• **HDR containers** (JPEG XR, AVIF, OpenEXR, HEIF) are not decoded. Folder import always lists files with the extensions `.jxr`, `.avif` and `.exr` in addition to the folder's extension filter; drag & drop, Ctrl+V and the file dialog recognise these formats by content. Once their size is stable they are set aside at once, without decode retries (R-CAP-1c). If a supported copy of the same capture is part of the same import (Game Bar writes a PNG next to the `.jxr`; pairing rule verified in M2, A16), the HDR file counts as "HDR original – SDR copy used" and needs no action. If the copy exists but was not imported, the message offers "Import the SDR copy". Otherwise the import result shows "n new, m skipped, k in HDR format" with the message "HDR screenshot format (JPEG XR/AVIF/EXR) – not supported", a hint that is tool-specific where the folder or file name identifies the tool (Game Bar: use the PNG next to it; NVIDIA overlay: reportedly JXR or a PQ-encoded PNG, use Game Bar or turn HDR off while capturing; gamescope: use the SC screenshot key or Spectacle; OBS on Windows: writes no SDR copy, use the SC screenshot key) or otherwise lists the alternatives, and a link to the capture tips (R-DOC-1). Messages offer only actions that exist.<br/>• Golden tests use synthetic decode fixtures (07 §4). | M |
| R-CAP-9 | **Capture check:** Diagnostics, and the onboarding as a skippable step after the folder selection (once OCR exists), offer "Check a screenshot". The user picks one screenshot of any commodity terminal. It is analysed with the normal pipeline but is **not** added to the queue or the processed-file register, and nothing is sent. The result lists, each with icon and text: file format and colour encoding (R-CAP-8), image size, panel located yes/no, measured price-digit cap height against the limits (R-OCR-17), tone state (R-OCR-18), and one concrete piece of advice per problem, worded per OS (from R-DOC-1). The same findings are shown per capture in the report editor via R-VAL-1/R-UI-4; there is no separate logic. | S |

## Recognition (OCR)

| ID | Requirement | Prio |
|---|---|---|
| R-OCR-1 | Local OCR (no cloud) with PaddleOCR models (detection + recognition) via ONNX Runtime; models bundled, license and hash evidence in `NOTICE` | M |
| R-OCR-2 | Localization of the terminal panel via text anchors and luma-gradient frame edges (no theme colour, R-OCR-18), perspective correction. If it fails, the user can set the corners or the crop manually; the app never aborts hard. | M |
| R-OCR-3 | Theme-agnostic: orange/red (e.g. Patch City/Pyro), blue and other terminal themes. Layout profiles are data-driven. | M |
| R-OCR-4 | Recognition of side (Buy / Local Market Value, active tab) and section (IN STOCK / OUT OF STOCK / IN DEMAND / NO DEMAND / SELLABLE CARGO) | M |
| R-OCR-5 | Robust number parser: strip currency symbol `¤`, determine thousands and decimal separators structurally, optional K/M suffix, suffix `/SCU` | M |
| R-OCR-6 | Repair of confusable digits ({0,6,8,9}, possibly others from the corpus), only with an unambiguous candidate and with a plausibility witness | M |
| R-OCR-7 | Commodity names are resolved against the UEX vocabulary and localized `global.ini` names. Robust against line breaks and overlap with the SCU value. | M |
| R-OCR-8 | Terminal and location recognition primarily from the location field under "YOUR INVENTORIES", matched against the assortment | M |
| R-OCR-9 | "AVAILABLE CARGO SIZE (SCU)" → `container_sizes` | S |
| R-OCR-10 | Second reader for the status: color and fill level of the vertical stock bar or the color of the status text, matched against the OCR status text | S |
| R-OCR-11 | Stitching of multiple scrolled screenshots of one terminal or side – **even without overlap** (order via the scrollbar, merging via the commodity ID). Cut-off cards at the edge are only taken over if the card is fully visible (bottom edge detected). On conflicts, the value read further away from the viewport edge is preferred. Possible gaps (scrollbar, UEX assortment) are shown. If two captures of the same report contain conflicting values for the same field, the **later capture wins** (finding `Superseded`, e.g. after the player's own trade); edge position only decides between captures taken within the same minute. | M |
| R-OCR-12 | Processing in the background (bounded parallelism), the UI never blocks. Goal: < 3 s per screenshot on a mid-range CPU (**target value, will be measured**). | M |
| R-OCR-13 | **Report grouping:** Scans belong to one report if terminal, side and environment are the same and the time gap to the previous scan of the group is ≤ 10 min (configurable). The user can split and merge reports in the UI. A scan with an unclear terminal forms its own group until the terminal is resolved. Captures never join a report that is no longer in state Draft; they start a new report. | M |
| R-OCR-14 | **Neighbor names** (distinguished only by a short token such as "SIZE 1"/"SIZE 7") are only assigned automatically if the distinguishing token was read exactly, otherwise `Ambiguous` (07 §2.5). | M |
| R-OCR-15 | Dimmed cards (hypothesis A14: not buyable) are read with their own contrast normalization and not discarded as a partial card. | S |
| R-OCR-16 | **Not a terminal screenshot:** images that do not show a commodity terminal (other UI, other app) are recognized as such and set aside with a notice and a "process anyway / crop manually" action – never a generic "failed to process" error (fix for F7). The notice names "terminal too far away or too small in the image" as a possible cause next to "other screen". A valid shop panel whose "YOUR INVENTORIES" field shows another location (ship, other station's storage) is **not** rejected: the terminal counts as unknown and the selection is mandatory (session context and assortment as hints). | M |
| R-OCR-17 | **Resolution and scale independence:** the measured text size decides whether a capture is readable, never its pixel dimensions.<br/>• **Covered inputs:** 1920×1080 up to 3840×2160, 21:9 and 32:9 (including native 7680×2160), multi-monitor desktops (e.g. 5760×1080), windowed captures (also below 1080p) and DSR/VSR captures above the monitor resolution. The image size is never assumed to equal a display or render resolution.<br/>• **Geometry:** the panel is located via text anchors and normalized by homography; all layout tolerances are relative to the normalized panel, never absolute pixels ([07](07-ocr-concept.md) §2.1 items 1, 4 and 6).<br/>• **Pixel budget:** an input above the budget (setting, start value 20 MP, so that native 7680×2160 is not reduced) is reduced by an integer box factor while decoding in `adapter-files` (info finding `Downscaled` with the original size), so that the heap budget (R-NF-3) holds. Inputs up to 7680×4320 never cause an out-of-memory error (resource test). The text-size gate runs on the raster that is actually read.<br/>• **Text-size gate:** the reference is the **cap height of the price digits** in source pixels. Before layout it is estimated from the anchors via per-theme ratios in the layout profile (Stanton blue, measured on the unverified entry `pyro-gateway-stanton-01`: price ≈ 0.84 × "SHOP INVENTORY" ≈ 1.13 × "AVAILABLE CARGO SIZE"). After layout it is measured on the price digits, and the **smallest value over the fully visible cards** counts (perspective changed it by 5–10 % between cards in the sample). The location field is gated the same way. Start values: **≥ 8 px** normal; **6 to < 8 px** (*confirm limit*) finding `SmallText`, numeric fields at most "confirm"; **< 6 px** (*lower limit*) finding `TextTooSmall`, numeric fields appear only as suggestions at level "correct" and are never part of "Accept all confident"; names are still resolved.<br/>• **Origin of the start values:** a preliminary box-downscale experiment during planning (one theme, third-party export of PP-OCRv6 small; nearest-neighbour downscaling was 1–2 px worse), so they may be optimistic for in-engine rendering. M2 calibrates them per theme with the official export ([04](04-roadmap.md) M2, 07 §4).<br/>• **Wording:** the finding text gives the measured value and the target and is advice for the **next** capture, never a demand to redo this one, e.g. "Text is small in this capture (price digits ≈ 7 px, reliable from 8 px). Values need confirmation. Next time move closer so the terminal screen fills about three quarters of the image height, or use a higher game resolution." The crop is always shown so the user can type the values.<br/>• The two limits are the only legibility thresholds on source-image content (legibility is absolute, so they are in source pixels). They live in a typed settings record that is not offered in the normal settings view. | M |
| R-OCR-18 | **HDR and tone variations:** recognition works with captures taken with HDR on or off. Files whose colour encoding is known to be HDR are handled by R-CAP-8, not here.<br/>• After locate, each located panel is **analysed and normalized per panel** ([07](07-ocr-concept.md) §2.1 item 7): black and white points from percentiles, saturated-stroke share and saturation relative to the layout profile's SDR reference. The normalized panel drives colour and geometry decisions; whether the recognizer gets the normalized or the original crop is decided by the M2 eval. Colour decisions (tab, status colour, hover) are relative comparisons within the panel and use hue/relative saturation, never absolute RGB thresholds.<br/>• **Two tone problems are detected separately:** **washed out** (raised black level and compressed range, typical for 8-bit captures of an HDR desktop and for untagged PQ-encoded files; recoverable by the stretch) gives the finding `LowContrastCapture`; **clipped** (glyph detail lost to saturation; calibrated so that ordinary SDR captures with white glyph cores do not trigger it) gives `ClippedHighlights`. Start rule: under either finding every numeric field gets at most "confirm"; M3 decides per finding whether the cap stays (07 §2.1 item 7).<br/>• The finding text names likely causes without claiming to know them, e.g. "possibly a screenshot of an HDR display, or very high in-game brightness/gamma", and links to the capture tips for the user's OS (R-DOC-1).<br/>• **Hints are non-modal.** The report editor shows them per capture. The queue shows one notice per input source (folder, drag & drop, clipboard) and session once N consecutive captures from that source carry the same finding (setting, start value 3), e.g. "Recent captures from <folder> look washed out – see capture tips". "Don't show again for this source" hides the notice, never the per-capture finding. | M |
| R-OCR-19 | **Layout validated per game version:** every layout profile lists the game versions it was validated on (corpus run). If a capture's game version is newer than all validated versions, every OCR field is capped below the send threshold (finding `UnvalidatedGameVersion`) until a release validates it; the user can lift the cap for the current session after a warning. This protects UEX when a patch changes the terminal UI in a way that still reads "cleanly". | M |

## Optional AI recognition (VLM)

The classic OCR (above) is the **default path** and always runs, even while playing. In addition, a **local vision language model (VLM)** can be enabled via [Ollama](https://ollama.com). It needs a lot of VRAM or CPU and therefore by default runs **only when Star Citizen is closed**. This way you can work in the game without AI and have the AI re-check afterwards.

| ID | Requirement | Prio |
|---|---|---|
| R-VLM-1 | Setting "AI recognition" with three values: **Off** (default), **Automatic – only when the game is closed**, **Always** (expert, with a warning about VRAM and FPS losses) | S |
| R-VLM-2 | Game detection: the process `StarCitizen.exe` is checked periodically (default every 5 s). Windows: path ends in `Bin64\StarCitizen.exe` (`ProcessHandle`). Linux: `/proc/<pid>/cmdline` (incl. argv[0]) or `/proc/<pid>/comm` of the Wine/Proton process contains `StarCitizen.exe` (assumption A7). If the game state **cannot be determined** (process list unreadable, unknown runner), it counts as RUNNING (fail-safe). The RSI Launcher alone does not count as "game running". "Closed" only applies after a hysteresis (default 30 s), so that a restart of the game does not start the AI. | S |
| R-VLM-3 | Game start during an AI run in mode **Automatic**: the running job is aborted immediately and the model unloaded (`keep_alive: 0`). Affected scans return to the state "AI pending"; no data is lost. | S |
| R-VLM-4 | Re-check after the game ends: the app offers (or runs automatically, configurable) to re-read all **not yet sent** reports with the VLM. Selectable are "only reports with warnings" (default) or "all". Only reports in state **Draft** are re-read; released, queued or submitted reports are never changed by the AI. Progress and cancellation are possible at any time. | S |
| R-VLM-5 | Fusion: VLM and classic OCR are **independent readers**. Agreement increases the confidence ("double confirmed"); contradiction creates a finding `Ambiguous` with both candidates. VLM values go through the **same** vocabulary resolution and validation (prior, tolerances, consistency). No reader alone enforces a value that contradicts the validation. | S |
| R-VLM-6 | Strictly local: default host `http://localhost:11434`, configurable. Cloud models (Ollama Cloud, suffix `:cloud`) and non-localhost hosts only after explicit confirmation with a privacy notice. Otherwise images never leave the computer. | S |
| R-VLM-7 | Model management: check Ollama reachability and version (`/api/version`), show installed models (`/api/tags`), pull the recommended model on request (`/api/pull` with progress). Ollama itself is **not** shipped; the app shows installation instructions. A minimum Ollama version is checked (below it the feature is disabled with a reason). Pulls show the download size and free disk space and need explicit confirmation. States "Ollama not installed / not running / model missing" are shown in the settings, never as startup errors. | S |
| R-VLM-8 | Hardware notice: after loading the model, `size_vram` is compared with `size` (`/api/ps`). If the model does not run fully on the GPU, the app warns ("slow, running on CPU"). The speed per image is shown in the UI. | S |
| R-VLM-9 | Input to the VLM is the **perspective-corrected panel crop** (shop panel or location field), not the whole screenshot. This is smaller and faster, and the balance is not passed along. | S |
| R-VLM-10 | Output format: prompt as a versioned resource; temperature 0; answer as `KEY: value` lines plus a Markdown table, processed by a deterministic parser (see [07](07-ocr-concept.md) §2.7). If the answer is truncated (`done_reason == "length"`), exactly one retry with a larger token limit follows. | S |
| R-VLM-11 | The recommended default model is determined by a **bake-off on our corpus** (not by model card). Candidates include `qwen3-vl:8b-instruct`/`qwen3-vl:4b-instruct`, tried and tested at basetool; their suitability for commodity terminals is **unproven**. | S |
| R-VLM-12 | The feature is fully optional: without Ollama the app is fully usable, without error messages at startup. (Applies from release 1.0 on, i.e. before the AI feature itself exists.) | M |

## Validation (VAL)

| ID | Requirement | Prio |
|---|---|---|
| R-VAL-1 | Rule-based confidence per field; the model's confidence values are not used directly. Every warning has a reason code that is shown in the UI. | M |
| R-VAL-2 | Plausibility against the UEX prior: a deviation > `price_variation` % or > `scu_variation` (from `data_parameters`; units per assumption A15) is never rejected automatically – it is marked as a **major deviation** and must be confirmed by the user before submission (R-UI-10). Genuine price changes are therefore possible, but never unchecked. | M |
| R-VAL-2a | **No prior available** (new commodity at the terminal, no history): as a substitute, the commodity-wide average (`commodities.price_buy`/`price_sell`) is used with double tolerance. If that is missing too, no prior-based repair takes place; the field carries the finding "no reference value" and lies below the send threshold if it contains a confusable digit. | M |
| R-VAL-2b | **Repairs only automatic with an independent witness:** A repair that relies only on the prior lies below the send threshold (confirmation by keystroke). It is only taken over automatically if an independent witness agrees (a glyph-topology classification of the digit, or the second reader/VLM; roles defined in 07 §2.5). Rationale: the prior is a possibly outdated value; otherwise genuine price changes would be silently "repaired back" to old values. | M |
| R-VAL-3 | Consistency rules: status ↔ SCU (e.g. "Out of Stock" ⇒ 0 SCU), side ↔ section, commodity is buyable or sellable at this terminal (`is_buyable`/`is_sellable`) | M |
| R-VAL-4 | Terminal ambiguity: if there are multiple candidates, the selection is mandatory; the app silently preselects nothing | M |
| R-VAL-5 | Missing commodities: commodities that are listed at the terminal according to UEX but do not appear on any scan are shown as "not observed". `is_missing` is offered **only** if the relevant section was captured expanded and the gap check shows full coverage; commodities in a collapsed section (e.g. OUT OF STOCK on the buy tab) are never offered for `is_missing`. | S |
| R-VAL-6 | **Observation age:** every report carries `observedAt` (oldest capture time). If its age at release or at a send attempt exceeds `maxObservationAge` (setting, start value 60 min, to be agreed with UEX), release requires a confirmation per report; above a hard limit (start value 24 h) sending is blocked. Queued jobs are re-checked before every attempt. | M |
| R-VAL-7 | **Fresh reference at release:** at release the submission gate re-runs with the current reference snapshot. Confirmations stay valid unless the deviation level gets worse. After a successful submission the local prior is updated with the submitted values. | M |

| R-UI-15 | **Connection test** in diagnostics: UEX reachability per host, HTTP status, API status field and body (secrets masked), proxy and truststore in use (fix for F20). | M |
| R-UI-10 | **Deviation marking against UEX:** Every field (price, SCU, status, container sizes) is compared with the previous UEX value for the same combination of terminal, commodity and side and **marked by color**. Levels:<br/>• **equal** – no marking<br/>• **deviating within tolerance** – subtle marking (yellow), notice "please cross-check"<br/>• **strongly deviating** (> `price_variation` % or > `scu_variation`, status ≥ 2 levels apart) – strong marking (orange) **and confirmation required** (submission block until confirmation)<br/>• **no reference value** (new at this terminal) – notice marking (blue)<br/>Applies equally to OCR and manual reports. Thresholds come from `data_parameters` or the settings, not from constants. | M |
| R-UI-11 | **Make cross-checking easy:** For marked fields the following are visible: UEX value, age of the UEX value ("3 days ago"), difference absolute and in % (e.g. "+12 %"), plus the image crop of the source. The marking is **not only colored** but additionally encoded as an icon and text (color vision deficiency). The colors are chosen to be suitable for color vision deficiency (no pure red/green) and configurable in the theme. An **outdated** UEX value (older than configurable, default 7 days) weakens the marking by one level and is shown as "reference outdated". | M |
| R-UI-12 | **Summary before submission:** The report shows at the top the number of deviating and strongly deviating fields; via keyboard you jump from deviation to deviation (same navigation as R-UI-5). A confirmation applies to exactly the confirmed value; if the value is changed afterwards, it must be confirmed again. In addition, **unexpected commodities** (unknown at UEX for this terminal) and **missing commodities** (listed at UEX, not found in the scan, R-VAL-5) are marked. | M |

## Submission (SUB)

| ID | Requirement | Prio |
|---|---|---|
| R-SUB-1 | `POST /data_submit` with `id_terminal`, `type`, `is_production`, `game_version`, `prices[]` (separate buy and sell rows), optionally `container_sizes`, `screenshot`, `details` | M |
| R-SUB-2 | Submission queue: rate-limit compliant (120 req/min global, max. 500 rows per report, at most 1000 report rows per 30 min – UEX counts each price row as a report), bounded parallelism, retry with backoff only on 429/5xx/network errors. | R-SUB-3 | Submission block on unresolved fields or an unclear terminal | M |

| R-SUB-5 | Before submission: check `data_parameters` (`is_accepting_reports` or `is_accepting_ptu_reports`, `commodity.is_accepted`). For this, a state at most 15 min old is used (not the daily cache), because these flags change on patch day. | M |
| R-SUB-6 | Mapping of all known UEX error codes to clear user messages (ResourceBundle keys) with a recommended action; unknown codes are shown with the raw code (fix for F22) | M |
| R-SUB-7 | Upload screenshot: perspective-corrected crop "SHOP INVENTORY" plus location field, **balance always redacted**, JPEG or PNG < 10 MB (target ~1–2 MP). For manual attachments before automatic locate exists (M1), the user selects the region and must confirm a **full-size preview** ("contains no balance or personal data") before release. | M |
| R-SUB-8 | Test mode (`is_production=0`), switchable in the settings. `is_production` is fixed on each report at release and shown on the report and history row; switching the mode does not change queued jobs; test submissions create no cooldown for production. Default: **on** in development builds and CI; **off** in release builds after onboarding (the onboarding offers a test submission first). The active mode is always visible in the UI. | M |
| R-SUB-9 | **Unknown outcome:** a request whose outcome is unknown (timeout or connection reset after the body was sent) is **not** retried automatically; the job becomes `OutcomeUnknown` and is resolved via `data_info` or by the user. A POST is never repeated against the fallback host. An `ok` response whose number of `ids_reports` differs from the number of rows is stored as `PartiallyAccepted` with a per-row mapping and shown to the user – never treated as full success. | M |
| R-SUB-10 | **Correction after submission:** if UEX `data_edit` is verified (06), a submitted row can be edited with a new confirmation; otherwise "withdraw" (`data_remove`) and "duplicate as new draft" are offered. | S |
| R-SUB-11 | **Error classes:** every UEX error belongs to exactly one class – *transient* (retry with backoff, incl. `requests_limit_reached` with HTTP 200), *account* (`invalid_secret_key`, `user_not_allowed`, `user_disabled`: pause the **whole** queue, ask for re-authentication), *acceptance closed* (`is_accepting_*` = 0: hold jobs, re-check every 15 min, subject to R-VAL-6), *report-fixable* (`invalid_game_version`, `screenshot_required`, `max_rows_exceeded`: back to Draft with a finding), *permanent* (Rejected, with "duplicate as new draft"). Unknown codes count as permanent. | M |
| R-SUB-12 | Queue entries, history and cooldowns are bound to the UEX user (`username` from `/user`). If the key changes to another user, the app asks what to do with queued jobs. | M |

## Quality assurance (QA)

| ID | Requirement | Prio |
|---|---|---|
| R-QA-1 | Golden corpus: real screenshots plus hand-transcribed expected values (JSON). **Storage location outside the public repo** if the images contain private data (balance!). If necessary, check in only redacted versions. | M |
| R-QA-2 | The corpus is captured as **ladders**, not as a cross product. From a base configuration (1920×1080, Windows HDR off, SC screenshot key, default renderer, no upscaler, default gamma/brightness/contrast, fixed FOV setting, terminal screen filling ≥ 75 % of the image height), each ladder varies exactly one factor. Each ladder is captured on ≥ 2 terminals (one blue, one orange theme), Buy and Sell, from the same standing position (capture protocol, [07](07-ocr-concept.md) §4).<br/>**Required for 1.0:**<br/>• resolution ladder: 1920×1080, 2560×1440, 3840×2160, 3440×1440 (21:9), 5120×1440 (32:9), one windowed capture (a class without a matching display stays `synthetic only`, R-QA-3);<br/>• distance ladder at 1080p: base distance, ×1.25, ×1.5, ×2 (calibrates the R-OCR-17 limits);<br/>• HDR ladder with three steps (Windows HDR off; Windows HDR on with game HDR off; both on) for each capture method recommended in R-DOC-1 and for Win+PrtScn (the most common washed-out case): SC screenshot key (DX11 and Vulkan, while both are selectable), Xbox Game Bar PNG, Win+PrtScn (Windows "SDR content brightness" at 0 and at the tester's normal value, recorded in `conditions`), Snipping Tool with the "HDR screenshot color corrector" off and on (if the installed version offers it);<br/>• themes: blue/uppercase (Pyro Gateway Stanton – first entry available), orange/red (Pyro, e.g. Patch City), Nyx, a Gateway; Buy and Sell; scrolling with and without overlap; long and nearly identical names; dimmed cards;<br/>• one full multi-monitor desktop capture and one Snipping Tool region capture.<br/>**Optional** (covered when hardware or tools are available): NVIDIA overlay, Steam screenshot, ShareX, OBS; native 7680×2160 and 5760×1080; Ref-White low/high; non-default gamma/brightness/contrast; upscaler (DLSS/TSR "Performance"); PTU/EPTU capture with burned-in build text; Linux (SC key, Spectacle, gamescope; HDR via Wine-Wayland or gamescope).<br/>Each capture is also assigned a **text-height band** from its measured price cap height (< 6, 6–8, 8–10, 10–14, ≥ 14 px). The band, not the resolution label, shows scale independence. A class counts as covered only with ≥ 4 verified captures from ≥ 2 terminals and ≥ 40 numeric fields (start values); below that its status is `insufficient` (R-QA-3). | M |
| R-QA-3 | Eval CLI: field accuracy per field type **and per corpus class** (each `conditions` dimension of [07](07-ocr-concept.md) §4, each text-height band and each synthetic variant), share of "silently wrong" (wrong and marked as confident; **target ≈ 0**), share of "flagged", runtime and peak heap per resolution class.<br/>• Every class row shows a **status**: `gated` (minimum samples of R-QA-2 reached and verified), `insufficient (n = …)`, `synthetic only` or `missing`, plus the number n of evaluated numeric fields and the number of captures. If silently wrong is 0, the row also shows its one-sided 95 % upper bound (≈ 3/n, rule of three), so "0 of 20" reads "< 15 %", not "proven". Fields of one capture are correlated, so this bound is optimistic and is read together with the capture count.<br/>• **CI gates:** (1) no field that was not silently wrong in the baseline becomes silently wrong, in **any** class including `insufficient` ones (per-field comparison with the checked-in `tools/ocr-eval/baseline.json`, from the M3 baseline on; the baseline changes only through a PR that includes the eval diff, and new corpus entries extend it in the same PR); (2) accuracy and flagged-share ratchets apply only to `gated` classes; (3) the metamorphic gate (07 §4).<br/>• A required R-QA-2 class that is `missing` or `synthetic only` never passes silently: the eval lists it, and the release checklist requires it to be named "not verified" in the release notes and in the user guide (R-DOC-1). | M |
| R-QA-4 | OCR digest test: hash of all raw OCR outputs over the corpus, so that model or runtime updates happen deliberately | S |
| R-QA-5 | **"Report a misread" export:** from the report editor the user can export the redacted panel crops plus the corrected values in the `expected.json` format; `corpus/README.md` describes how such exports enter the corpus. This is how real-world misreads feed the regression corpus. | S |
