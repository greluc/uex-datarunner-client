# Requirements

> **Doc type:** Living spec — binding. Last reviewed: 2026-10-26.

Priorities: **M** = Must (1.0), **S** = Should (1.x), **C** = Could (later).

Amended 2026-10-12 ([ADR-0005](../adr/0005-rust-and-egui.md)): the implementation is Rust with egui, native code only by registered exception. Requirements whose meaning changes (R-UI-17, R-NF-1, R-NF-3, R-NF-12, R-SEC-1 to R-SEC-3, R-SEC-8, R-SEC-10) carry an `Amended 2026-10-12 (ADR-0005)` note; where only the technology wording changed (Java, JavaFX, Gradle, jpackage and similar terms replaced by their Rust equivalents or by neutral wording), this note covers the change and a row may add "Wording amended 2026-10-12 (ADR-0005)". The behaviour, the IDs and the priorities are otherwise unchanged. Choices that ADR-0005 leaves open (crates, message-catalogue format, decoder and ICC libraries) are chosen and verified at source in M0.

IDs are stable and never reused or renumbered. A dropped requirement keeps its row with the priority `Withdrawn (YYYY-MM-DD)`, the reason and its replacement; a new requirement takes the next free number in its area ([CLAUDE.md](../../CLAUDE.md), "Requirements, decisions and open points"). Open owner decisions and verifications are tracked in [docs/adr/0000-open-points.md](../adr/0000-open-points.md); the assumptions stay in this document.

## Goal

Players (UEX DataRunners) use the client to capture commodity terminal data from Star Citizen and provide it to UEX. There are two ways to do this:

- **manually:** fast, keyboard-driven input, with current UEX values shown as reference (not prefilled, R-MAN-2)
- **via screenshot:** OCR, validation, review, submission

Current UEX data (terminals, commodities, latest prices, status levels, game version, tolerances) serve as **default values and constraints** for recognition and selection.

## Terms

The complete, binding domain language (Ubiquitous Language) is in [11-ddd-and-tdd.md](11-ddd-and-tdd.md) §A1. Only the short version here:

| Term | Meaning |
|---|---|
| **Capture** | A screenshot |
| **Scan** | A capture after OCR analysis |
| **Report** | The aggregation of all scans of one terminal, one side (buy = "Buy", sell = "Local Market Value") and one environment within a time window (grouping rule R-OCR-13). The report is the unit sent to `POST /data_submit`. |
| **Send threshold** | Minimum confidence at or above which a field may be sent without confirmation (initial value 0.80, see [07](07-ocr-concept.md) §2.6). Mandatory fields ([11](11-ddd-and-tdd.md) §A1) below it must be confirmed or corrected; an optional field below it is not sent. |
| **Prior** | The latest UEX value (price, SCU, status) for the combination of terminal, commodity and side, with its age; without one, the commodity-wide average price is a coarse substitute (R-VAL-2a) |

| R-CAP-1c | **Read only when fully written:** A file counts as complete when its size and `lastModified` are stable for a quiet period (default 750 ms) and it can be decoded as an image. Files whose content is an unsupported format (R-CAP-8) are not retried: once their size is stable they are set aside at once with the R-CAP-8 message. | R-CAP-1d | **Processed-file register** (SQLite): path, size, `lastModified` and content hash of every imported file. From R-CAP-10 on (M4), the folder's environment is cross-checked with the running game's channel. | M |
| R-CAP-3a | **Environment mapping to UEX:** UEX only knows `live` and `ptu`. Default mapping: LIVE and HOTFIX → `live`, PTU/EPTU/TECH-PREVIEW → `ptu`. Verified 2026-10-25 (A9): UEX accepts exactly the version `data_parameters` names for `live`, or for `ptu` while PTU reports are open, whatever the launcher calls the build; an EPTU or Tech-Preview build counts only when its version equals the `ptu` version, which the version check of R-CAP-3b enforces. If no reports are accepted for the target (`is_accepting_*` = 0 or `commodity.is_accepted` = 0), release still works and the jobs are held until acceptance reopens (R-SUB-5, R-SUB-11). | M |
| R-CAP-3b | **Game version at capture time:** the app keeps a persisted history of observed versions **per UEX environment** (`live`/`ptu`): version, first seen, last seen – only from successful `game_versions` fetches, never from the cached state. Besides the TTL refresh ([06](06-uex-api.md)), `game_versions` is fetched at startup, before an import batch is versioned if the last successful fetch is older than `versionStampMaxAge` (setting, start value 30 min), when the game starts (R-VLM-2) and at most 15 min before every send attempt (R-SUB-5). Until the first successful fetch after installation (e.g. an offline first start, R-UI-13), new captures wait in state `Imported` and are neither versioned nor scanned; that fetch moves them to `Ready` or "environment pending" (default until the owner decides). Each capture gets the version for its capture time t (R-CAP-5) and environment, derived once the environment is known ("environment pending", R-CAP-1):<br/>• **certain:** t lies between first and last seen of one version;<br/>• **provisional:** t is after the last successful fetch; the newest version is used, and the next successful fetch makes it certain (same version) or uncertain (new version);<br/>• **uncertain:** t lies between the last seen of one version and the first seen of the next (e.g. a catch-up import after a patch), or before the oldest observation (including an empty history after the first install, where the version is assigned at the first successful fetch); an uncertain capture time (R-CAP-5) makes the version uncertain as well, and so do different versions among the captures of one report (a patch inside the grouping window);<br/>• **unknown:** UEX reports no version for the environment (e.g. `ptu` is `null`); release is blocked until a version is observed or the report is discarded.<br/>A report with an uncertain version, or whose version is no longer the newest observed one (patch between capture and sending), is marked "to be checked" (I5), and release requires the user's choice. A queued job that meets a version change at a send attempt returns to Draft marked the same way (R-SUB-5) and shows in the queue, never through a dialog (R-UI-16). The choice is made on the report (I5): the user keeps the capture-time version, switches an uncertain version to another version from that environment's history observed around the capture time, or discards the report (state `Discarded`, reason version changed). Once the user confirms or enters an uncertain capture time (R-VAL-6), the version valid at that time is used. The report is sent with the chosen version and never silently relabelled with the current one. UEX rejects every version but the current one with `invalid_game_version` (A18 refuted 2026-10-25), so keeping a capture-time version that is no longer the newest observed one is not offered: such a report can only switch an uncertain version, as above, or be discarded. The order of versions comes only from this observed history (first and last seen); version strings are never parsed or compared, because UEX strings are not always three-part ("4.9", "3.24.2a"). `/game_versions_all` is used only to measure A17, never to seed or reorder the history (decided 2026-10-09, O-99). Known gap: if UEX publishes a new version late, or a patch keeps the version string, captures get the old version (A17). | M |
| R-CAP-4 | Automatic detection of the SC installation: RSI Launcher log `Launching Star Citizen … from (…)`, running process `Bin64/StarCitizen.exe`, default paths. On Linux additionally Wine/Proton prefixes (see assumption A3). | S |
| R-CAP-5 | **Capture time with its source** (`CaptureTime`):<br/>• **FILE_NAME:** a listed, tested file-name pattern per known tool (SC screenshot key and the tools recommended in R-DOC-1; patterns verified with real files, A19), read as local time in the system time zone and converted with the zone rules. If it is ambiguous (autumn DST overlap), the offset whose instant is closest to `lastModified` is used; if neither candidate lies within a tolerance (capture settings record, start value 2 min), the earlier instant is used. If the local time does not exist (spring DST gap), or it is later than `lastModified` by more than the tolerance (zone or clock mismatch), `lastModified` is used. These three cases (overlap, gap, mismatch) make the time uncertain (see below). A file-name time earlier than `lastModified` is normal for copies and is not flagged. Tests use a fixed `Clock` and zone (Europe/Berlin around 2026-10-25 and 2026-03-29);<br/>• **FILE_MTIME:** `lastModified`;<br/>• **CLIPBOARD_EVENT:** the time at which clipboard monitoring detected the change (the image appeared while the app was running);<br/>• **PASTE_TIME:** the time of Ctrl+V or of dropping image data without a file (no information about the capture);<br/>• **USER:** entered or confirmed by the user (R-VAL-6).<br/>The time counts as **certain** for FILE_NAME (except in the three overlap, gap and mismatch cases), CLIPBOARD_EVENT and USER, and for FILE_MTIME of a file the watcher saw appear while the app was running (mtime within a tolerance of the first sighting; setting). Otherwise – those three FILE_NAME cases, FILE_MTIME from the catch-up scan, "Import", drag & drop or the file dialog, and PASTE_TIME – the capture gets the finding `CaptureTimeUncertain` (R-VAL-6), because copied, downloaded or synced files can carry the time of the copy and pasted image data carries none. The source is shown in the queue and the report editor. Grouping (R-OCR-13), sessions (R-UI-14) and the "only files newer than" filter (R-CAP-1) use the same capture time. The app detects duplicates via content hash. | M |
| R-CAP-6 | Optional cleanup function: delete or archive originals after successful submission. Default is **off**. | S |
| R-CAP-7 | **Working copies:** Per capture, the app stores the perspective-corrected panel crops (not the full-screen screenshot) in its data directory, at about 1:1 source scale so that re-reads keep the source legibility. The crops are stored **redacted**: their extent and the header-band fill follow R-SUB-7 and are applied before anything is persisted. Review, AI re-check, upload and the exports (R-QA-5, R-NF-6) use only these crops, never the original. Upload, AI re-check and review therefore also work if the original was moved or deleted. **Retention** (periods are settings, counted from the last state change):<br/>• **never purged automatically:** working copies of reports in Draft, Released, Queued, WaitingForCooldown or OutcomeUnknown (including jobs held or paused, R-SUB-11), and of captures not yet scanned (e.g. environment pending);<br/>• **7 days:** working copies of reports in Submitted, PartiallyAccepted, Rejected or Withdrawn, of discarded reports (state `Discarded`, counted from the discard) and of failed captures;<br/>• **1 year:** history metadata;<br/>• **evidence-dependent actions:** "duplicate as new draft" (R-SUB-10, R-SUB-11) and the R-QA-5 export are offered only while the working copies exist; the duplicate keeps the original `observedAt`, so R-VAL-6 still applies. Drafts older than the R-VAL-6 hard limit are offered for discard, never discarded automatically;<br/>• **disk space:** before writing working copies, the app checks the free space of the data directory against a threshold (setting; start value set in M3 from measured working-copy sizes). Below it, import pauses with a visible needs-action state on the folder status and in the queue; working copies of open reports are never deleted to make room. Diagnostics shows the size per retention category. | M |
| R-CAP-8 | **Image formats and colour encoding:** the format is detected from the file content (magic bytes), not from the extension.<br/>• **Read:** PNG (8 and 16 bit per channel), JPEG (reportedly the format of the SC screenshot key, A16) and BMP, converted to an 8-bit sRGB `ImageRaster`; 16-bit samples are scaled from the full 16-bit decode, never truncated to the high byte.<br/>• **Colour metadata is evaluated explicitly** in `adapter-files` (a Rust decoder that exposes the colour chunks, or a small PNG chunk walker before `IDAT`), because a decoder does not apply PNG `iCCP`/`gAMA`/`cHRM` to the pixels by default and may not know `cICP`. The decoders and the ICC library are pure Rust where a mature one exists (ADR-0005 D1) and are chosen and verified at source in M0. PNG precedence: `cICP` > `iCCP` > `sRGB` > `gAMA`/`cHRM` (PNG 3rd edition). `iCCP` is applied through the ICC library; a JPEG APP2 ICC profile is applied by the same step (pinned by a decode fixture, [07](07-ocr-concept.md) §4); `gAMA` is applied; `cHRM` primaries other than BT.709 (without `iCCP`/`cICP`) count as an encoding the adapter cannot convert.<br/>• **Never read as sRGB:** a `cICP` with PQ (16) or HLG (18) transfer (e.g. `09 10 00 01`), any other `cICP` except BT.709 primaries (1) with sRGB transfer (13), and any other encoding the adapter cannot convert. In 1.0 such a file is set aside with the reason "HDR or unsupported colour encoding – use an SDR copy". A tone-mapping path (PQ EOTF, BT.2020 → BT.709, reference white 203 cd/m² by default, highlight roll-off, sRGB OETF; parameters in a settings record) is a 1.x option and needs an ADR on where it lives (adapter or a core HDR raster type).<br/>• **HDR containers** (JPEG XR, AVIF, OpenEXR, HEIF) are not decoded. Folder import always lists files with the extensions `.jxr`, `.avif` and `.exr` in addition to the folder's extension filter; drag & drop, Ctrl+V and the file dialog recognise these formats by content. Once their size is stable they are set aside at once, without decode retries (R-CAP-1c). If a supported copy of the same capture is part of the same import (Game Bar writes a PNG next to the `.jxr`; pairing rule verified in M2, A16), the HDR file counts as "HDR original – SDR copy used" and needs no action. If the copy exists but was not imported, the message offers "Import the SDR copy". Otherwise the import result shows "n new, m skipped, k in HDR format" with the message "HDR screenshot format (JPEG XR/AVIF/EXR) – not supported", a hint that is tool-specific where the folder or file name identifies the tool (Game Bar: use the PNG next to it; NVIDIA overlay: reportedly JXR or a PQ-encoded PNG, use Game Bar or turn HDR off while capturing; gamescope: use the SC screenshot key or Spectacle; OBS on Windows: writes no SDR copy, use the SC screenshot key) or otherwise lists the alternatives, and a link to the capture tips (R-DOC-1). Messages offer only actions that exist.<br/>• **Rules from the decoder check** (O-129): a `cICP` 1/13 at narrow range is expanded to full range (ITU-T H.273, samples outside 16 to 235 clipped); a PNG with `mDCV` or `cLLI` but no `cICP` counts as HDR-encoded, checked before `iCCP`; an ICC profile whose `cicp` tag names a PQ or HLG transfer counts as HDR-encoded (a rule for PQ or HLG profiles without that tag follows in M2); a colour chunk or JPEG APP2 ICC segment that is present but cannot be parsed, and a BMP V4/V5 header with a colour space other than `LCS_sRGB`, `LCS_WINDOWS_COLOR_SPACE` or `LCS_CALIBRATED_RGB` with empty calibration, count as encodings the adapter cannot convert.<br/>• Golden tests use synthetic decode fixtures (07 §4).<br/>Wording amended 2026-10-12 (ADR-0005): decoder and ICC terms; the M0 spike checks HDR and format detection with the Rust decoders against the fixtures. Amended 2026-10-14 (@greluc, O-129): the rules from the decoder check. | M |
| R-CAP-9 | **Capture check:** Diagnostics, and the onboarding as a skippable step after the folder selection (once OCR exists), offer "Check a screenshot". The user picks one screenshot of any commodity terminal. It is analysed with the normal pipeline but is **not** added to the queue or the processed-file register, and nothing is sent. The result lists, each with icon and text: file format and colour encoding (R-CAP-8), image size, panel located yes/no, measured price-digit cap height against the limits (R-OCR-17), tone state (R-OCR-18), and one concrete piece of advice per problem, worded per OS (from R-DOC-1). The same findings are shown per capture in the report editor via R-VAL-1/R-UI-4; there is no separate logic. | S |
| R-CAP-10 | **Environment cross-check with the running game:** the process monitor (R-VLM-2) also records the channel folder of the running game from the executable path (`…\StarCitizen\<CHANNEL>\Bin64\StarCitizen.exe`; on Linux from argv[0], A7) with timestamps, persisted next to the version history (R-CAP-3b); a channel it cannot determine is "unknown". On import, if a known channel was observed at the capture time and maps (R-CAP-3a) to another UEX environment than the folder's environment, the capture waits as "environment pending" (R-CAP-1) with the observed channel offered as a suggestion, not preselected. For a manual report, a running channel that maps to another UEX environment than the selected one is highlighted, and release needs an explicit confirmation of the environment. The confirmation is stored on the report with the observed running channel and the time; at release, the running channel's environment is compared with the report's, and release is refused with `EnvironmentUnconfirmed` while they differ and the report holds no confirmation for that running channel; a different running channel at a later release needs a new confirmation, and changing the report's environment revokes it (default until the owner decides). No observation, or an unknown channel, never counts as a mismatch. Until this exists, the environment is not cross-checked. | S |

| ID | Requirement | Prio |

| R-MAN-1 | Terminal selection via search field (fuzzy over name, nickname, `displayname` – the name shown on the terminal screen –, location, system), filter by star system, "recently used". This way no outdated values end up unchecked at UEX as a "fresh" report. An "Add commodity" action picks from the global vocabulary (`GET /commodities`, filtered only by availability in the report's environment; decided 2026-10-09: not by the global `is_buyable`/`is_sellable` flags, which disagree with real terminal rows, [06](06-uex-api.md)). Such a row gets the R-UI-10 level "no reference value", counts as an unexpected commodity in the R-UI-12 summary and is never added automatically. | M |
| R-MAN-3 | Full keyboard operation: Tab/Enter, number shortcuts for status levels 1–7 | M |
| R-MAN-4 | Manual reports go through the same validation (VAL) as OCR reports | M |
| R-MAN-5 | Manual reports can attach a screenshot. If the client knows that a screenshot is mandatory for the user (evaluation phase of new DataRunners, `screenshot_required`), this is shown in advance and submission without an image is blocked. Sources, in order: a verified field from `/user` ([06](06-uex-api.md) open point 10); otherwise the most recent `screenshot_required` answer for this account (stored with its date, from a real or test submission). Without such a source, a manual report without an image may be released; a `screenshot_required` answer returns it to Draft with a finding (R-SUB-11), and the requirement is remembered from then on. The stored flag is shown with its date, and the user can clear it ("try without screenshot"). UEX checks the screenshot requirement in test submissions too, so the onboarding's test submission can reveal it ([06](06-uex-api.md) open point 10); `GET /user` has no such field. (Assumption A11.) | M |
| R-MAN-6 | Manual reports have an environment and use the current UEX game version of that environment. There is no fixed default: the environment of the user's last manual report is preselected and shown prominently in the entry view and in the release summary; on first use the user chooses it. Once R-CAP-10 exists (M4), a running game on another channel is flagged. | M |

## Recognition (OCR)

| ID | Requirement | Prio |
|---|---|---|
| R-OCR-1 | Local OCR (no cloud) with PaddleOCR models (detection + recognition) via ONNX Runtime; models bundled, licence and hash evidence in `NOTICE` | M |
| R-OCR-2 | Localisation of the terminal panel via text anchors and luma-gradient frame edges (no theme colour, R-OCR-18), perspective correction. If it fails, the user can set the corners or the crop manually; the app never aborts hard. | M |
| R-OCR-3 | Theme-agnostic: orange/red (e.g. Patch City/Pyro), blue and other terminal themes. Layout profiles are data-driven. | M |
| R-OCR-4 | Recognition of side (Buy / Local Market Value, active tab) and of the section per card (IN STOCK / OUT OF STOCK / IN DEMAND / NO DEMAND / SELLABLE CARGO), from headers inside the shop panel only ([07](07-ocr-concept.md) §2.3, §2.5b). The content of SELLABLE CARGO and of a shop-panel NO DEMAND section is unverified (A21). | M |
| R-OCR-5 | Robust number parser: strip currency symbol `¤` (glyph box aligned with the recognised characters, [07](07-ocr-concept.md) §2.4), determine thousands and decimal separators structurally, optional K/M suffix, suffix `/SCU`. | R-OCR-6 | Repair of confusable digits ({0,6,8,9}, possibly others from the corpus): repair candidates only at uncertain confusable positions (definition in [07](07-ocr-concept.md) §2.5), only with an unambiguous candidate, and automatically only with an independent witness (R-VAL-2b) | M |
| R-OCR-7 | Commodity names are resolved against the full UEX vocabulary of the environment and the localised `global.ini` names, before and independently of any terminal assortment ([07](07-ocr-concept.md) §2.5). Robust against line breaks and overlap with the SCU value. Resolution always tries the English and the localised names, whatever the game's UI language. A vocabulary name that is a word prefix of another ("Diamond"/"Diamond Laminate") is accepted only when the card's name block has no continuation line; otherwise the field is `Ambiguous`. Possible truncation of long names on the kiosk (unverified) is checked on the corpus (decided 2026-10-09, O-96, O-104). | M |
| R-OCR-8 | Terminal and location recognition primarily from the location field under "YOUR INVENTORIES", matched against location names and terminal `displayname`s. Every candidate, including a single one, is checked against its assortment for the captured side by containment ([07](07-ocr-concept.md) §2.5 item 2). A location or `displayname` shared by several terminals is `Ambiguous` unless the assortment check singles out one of them. A screen whose location resolves only to refinery (`commodity_raw`) terminals is recognised as unsupported and set aside with that reason, never sent (decided 2026-10-09, O-96). | M |
| R-OCR-9 | "AVAILABLE CARGO SIZE (SCU)" → the row's `container_sizes`. Each sent row carries its own set when the set passes I2, and no field otherwise; UEX then keeps the sizes it has on record for that row ([11](11-ddd-and-tdd.md) §A1 "Mandatory field"; decided 2026-10-26, O-136, which withdrew the one-report-per-set split of O-92, because UEX reads the field per row, [06](06-uex-api.md) open point 9) | S |

## Optional AI recognition (VLM)

The classic OCR (above) is the **default path** and always runs, even while playing. In addition, a **local vision language model (VLM)** can be enabled via [Ollama](https://ollama.com). It needs a lot of VRAM or CPU and therefore by default runs **only when Star Citizen is closed**. This way you can work in the game without AI and have the AI re-check afterwards.
